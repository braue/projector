RTAC Tags, Quality & the Tag Processor

The RTAC's tag database — IEC 61850-flavored tag structures, the q and t attributes, and the Tag Processor grid that moves everything between protocols

☰The rules, stated plainly

  • Everything in the RTAC is a tag. Client tags, server tags, system tags, virtual tags, and logic variables all live in one database; nothing flows between them unless the Tag Processor (or your logic) moves it.
  • A tag is a structure, not a value: .stVal/.instMag plus .q (quality) and .t (timestamp). Map the whole structure and quality and time ride along; do math on bare values and you lose both.
  • Quality flows with the data — source tag to destination tag for statuses/analogs/counters, but server to client for controls.
  • Controls fire on a rising edge of oper*.ctlVal; the value must return low before it can fire again.
  • The Tag Processor runs every task cycle and completes all assignments before handing data to the protocols. Nothing updates faster than the task cycle time.

1The tag database: every path runs through it

Data in the RTAC are referenced by database points called tags, associated with client or server protocols, system values, global variables (including virtual tags), or user logic. Most tags — device tags, system tags, virtual tags, GVL tags — are global, visible to every RTAC process; only variables declared inside user-defined functions are local. Every protocol client fills tags, every protocol server publishes tags, and every logic block reads and writes tags. The Tag Processor is the switchboard between them: data flow from source tags (typically client/IED devices) to destination tags (typically server devices — SCADA masters, HMIs) once per processing cycle.

Naming: device.tag.attribute

Device tag names are always devicename_protocol.pointname — the device name concatenated with the protocol, a period, then the point: Relay1_DNP.AI_0000. Attributes chain on with further periods: Relay1_DNP.AI_0000.instMag, .q.validity, .t.value.dateTime. The tag is self-describing. You can rename devices and points but not the shape; alias tags escape the format entirely (assign in each device's Alias column — unique, starts with a letter, letters/numbers/underscores only, no double or trailing underscores, no special characters — and the alias replaces the tag name system-wide). System tags read as SystemTags.CPU_Burden_Percent.stVal; each device task's POU pins read as DeviceName_POU.Offline.

2Tag structures: the IEC 61850 flavor

RTAC data classes follow the IEC 61850 CDC idea closely: every point carries value plus quality plus time. The measurement/status classes (the everyday ones):

And the control classes — a bundle of oper structures plus a status readback:

Every operSPC holds ctlVal (BOOL — the edge that fires it), q, t, pulseConfig (cmdQual pulse|persistent, onDur, offDur, numPls), and origin (an orCat_t originator category: bay/station/remote/automatic/maintenance/process…).

3Quality: the q attribute in depth

q memberValues
validitygood, invalid, reserved, questionable
detailQual8 flags: overflow, outOfRange, badReference, oscillatory, failure, oldData, inconsistent, inaccurate
sourceprocess, substituted
testBOOL
operatorBlockedBOOL (Tag Processor has a dedicated column to drive it)

The built-in ValidityCheck() function encodes the detail→validity rules: an OR of overflow / badReference / failure forces validity := invalid; an OR of oldData / outOfRange / oscillatory / inconsistent / inaccurate (when not already invalid) yields questionable. MERGE_q() ORs every quality bit of two inputs to produce the worst case — use it when one destination is derived from several sources.

How quality propagates

  • Statuses, analogs, counters: destination-tag quality comes from the source (IED) tag — the Tag Processor copies value, quality, and time together when you map tag to tag. A Quality Source column can override it with any tag's .q.
  • Comm failure: when a client connection dies, the device's Offline POU pin asserts (for DNP: application-confirm timeout, link-status timeout, or transmission error, until a frame is again received) and downstream consumers see the bad quality — the manual's own examples guard with IF NOT Line_1_POU.Offline and SEL Line_1_DNP.AI_0000.q.validity = GOOD to fail over to a backup relay. Mirrored Bits states it hardest: on a detected channel/port failure the validity of all MB tags is set to invalid and status values follow the per-point Channel Fail State setting. Flex Parse likewise sets quality invalid on a parse failure.
  • Controls run backward: control-tag quality is provided by the server tags and transferred to the client tags — an IED's control tag inherits invalid quality if the SCADA server connection is down, even when the client link is healthy.
  • Onward to servers: server protocols treat quality as data — the IEC 60870 server, for instance, detects events on changes of .q.validity and .q.detailQual, not just value. (DNP flag mapping specifics: see DNP3 on the RTAC in atlas.)
  • Logic can destroy quality: BI_0000.stVal OR BI_0001.stVal yields a bare BOOL — time and quality of both inputs are lost. Use the structure-aware functions (AND_SPS, OR_SPS, ADD_MV, … §5) which merge q worst-case and keep the most recent t.

Quality propagation: the device drops offline, the client tag's q.validity goes invalid, and the same flag reaches the SCADA point, the HMI, and the logic guard — which refuses to act on a value it can't trust. ▶ Animated in the HTML edition.

4Timestamps: the t attribute

Every tag's t is a timeStamp_t:

t memberContents
valuedateTime (DT) + uSec — the stamp itself, microsecond field included
qualityleapSecondsKnown, clockFailure, clockNotSynchronized, accuracy (enum T0=10 ms … T5=0.001 ms, or unspecified) — a clock's confession about itself
sourcetimeSource: Null, IRIG_B, NTP, DNP, Free_Running, IED_Protocol, i870, PTP + priority — the stamp says where its time came from
DST / UTC_OffsetDaylight-savings enabled/activated/offset; UTC offset in minutes
  • Who stamps? Event-carrying protocols deliver the device's own timestamp (source IED_Protocol/DNP); values without one get stamped by the RTAC as they change. For an MV, t is the time of the last dead-band excursion — the moment mag last updated. (Whether a relay's DNP timestamp is scan time or true SER time is a relay question — see DNP3 Fundamentals in atlas.)
  • Tag Processor override: the Time Source column assigns any tag's .t (or System_Time) to the destination, overriding the source tag's stamp; Time Offset adds a constant T#… to it. The manual warns that using a different time source when mapping non-control types onto control types can cause incorrect control behavior.
  • Auto-Fill Time and Quality Source: an Options toggle — when the destination has status+q+t but the source maps only a status, it wires the quality and time source columns automatically so the destination gets stamped updates with good quality instead of empty ones.
  • Utility: TS_DIFF(t2, t1) returns the difference of two timestamps in logic or the grid.

5The Tag Processor itself

A spreadsheet-like grid, two main columns: Destination Tag Name (left — data leaving, typically server tags) and Source Expression (right — data entering, a tag or any IEC 61131-3 structured-text expression). Each row is an assignment; the RTAC completes all rows each processing cycle before passing data to the protocols, so protocols always see a consistent snapshot. Row order is the default solve order; a Solve Order column can override it. Mapping here does not dictate point order in any protocol — that lives in the device/map configuration.

  • Capacity: up to 10,000 rows; the POU-capacity gauge reads 100% at 300,000 characters of generated structured text. Over that, copy the generated code (Code tab) into a custom-logic program and delete the grid rows.
  • Logic in the grid: any structured text — IF/ELSE primary/backup selection on the Offline pin, SEL(q.validity = good, backup, primary) quality-based selection, Boolean combinations, scaling math. Define inline locals by typing TEMPVAL : REAL in the SE Data Type column. Access single bits with .0….31 suffixes. Always review the generated code in the Code tab after saving — look for "invalid statement" warnings (or set Treat Code not Generated as Error to make them fail the compile).
  • Structure-aware functions: whole-tag math that a bare + can't do — ADD_MV/INS/CMV, SUB_*, MULT_*, DIV_*, SCALE_MV/INS/CMV/BCR, AND/OR/NOT/XOR_SPS, OR_operSPC, vector helpers, MERGE_q, TS_DIFF. Their outputs carry the merged worst-case q and the most recent t of the inputs.
  • Per-row conditioning columns: Dead Band and Zero Dead Band (MV/CMV — the excursion moves instMag to mag), the four Range limits, PU/DO delay (T#10ms…T#1000000s debounce), Quality Source and Time Source overrides, Operator Blocked, and for control rows: Control Type (Pulse|Persist), On/Off Pulse Duration, Number of Pulses.
  • Logging & HMI columns: Logging Enable puts value changes in the SOE log (on/off messages, alarm flagging into the web Alarm Summary, and a chatter filter — N changes within Chatter Time mutes the point for 10× that window). Live Data Enable = Viewable or Forceable exposes the row on the web interface's Live Data page. The first rows of every project come preconfigured to log SystemTags security events — SEL recommends keeping them for NERC CIP.
  • Bulk entry: autocompletion, or paste whole columns from device Tags tabs, Excel, or a SCADA database export; pasting grows the grid automatically.

Execution timing

Tag values — controls included — update once per task cycle interval; nothing beats the cycle time. Cycle times that divide evenly into one second lock to the top of the second. By default everything runs in the main task cycle; selected device tasks can move to the faster automation task cycle, but tags cannot be mapped directly between the two cycles (cross-task data needs the CrossTaskData mechanism). Size the main cycle to at least 140% of the measured overall task timer — an overrun doesn't drop tasks, it steals time from following cycles and degrades web/HMI response.

6Controls plumbing: the round trip

A SCADA operate is just a write into a server control tag's oper structure, moved by the Tag Processor like any other data — only the quality flows the other way.

Control round trip: SCADA writes the server tag's operTrip.ctlVal; the Tag Processor row carries the edge to the client control tag; the client issues the protocol operate; the relay's status point comes back through an ordinary input mapping. ▶ Animated in the HTML edition.

  • Edges, not levels. A rising edge on operSet.ctlVal sets, on operClear.ctlVal clears; a held-TRUE does nothing more and must go low before the next fire (the manual's Mirrored Bits walkthrough: T‑0 set → status TRUE; T+1 set again → no change; T+2 clear → status FALSE).
  • Map the whole structure to pass DNP controls transparently (all five verbs). Converting between verb families — SCADA sends trip/close, the IED wants latch on/off — is a Control Type column change on the row (source and destination control types must match). Feedback: the .status member is an input the RTAC fills like any other status mapping; nothing updates it automatically.
  • Cross-protocol best fit: the Simple Tag Mapper extension automates dissimilar control classes (Auto mode): e.g. a DNP operClose lands as operSet on an SRBC remote bit, operTrip as operClear; a DNP operPulse onto an SBRC breaker bit is a documented no-op. Auto-Paired maps DNP BOs to trip/close remote-bit pairs; Verbose exposes every operSPC element for hand mapping.
  • Protocol specifics — CROB verbs, SBO vs direct operate, pulse execution on contact outputs — live in DNP3 on the RTAC and DNP3 Controls in atlas.

7System, virtual & diagnostic tags

Device health: POU pins

Every client/server task exposes pins on its Controller tab, readable in logic as DeviceName_POU.Pin. The ones worth alarming on: Offline (for a DNP client: asserts on application-confirm timeout, link-status timeout, or transmission error until a frame is received again — but note it can read False while a settings mismatch still blocks real data), Message_Failure_Count, ENO (task running at all). The web interface's Connected IEDs report shows the same truth as icons: green = communicating (Offline FALSE), red = comm failure (Offline TRUE), gray = disabled (ENO FALSE).

Virtual tags: internal plumbing

Virtual tag lists hold global tags of the same structured types as protocol tags (SPS, MV, SPC…) without belonging to any device — the clean way to buffer values between protocols, stage computed points, or hand data between the Tag Processor and logic. Up to 30 virtual tag lists per project (100 on SEL-3555/SEL-3350). For plain IEC types, use a GVL under User Logic instead; for RTAC-to-RTAC sharing, an NGVL broadcasts a variable list over Ethernet.

8Troubleshooting & fine print

  • Value looks right, downstream says stale/invalid → you mapped an attribute (.stVal, .instMag) instead of the whole tag, or built an expression that returns a bare value — quality and time didn't ride along. Map structures, or set Quality/Time Source columns, or use the structure-aware functions.
  • Control does nothing the second time → ctlVal never went low; edges only.
  • Control quality invalid at the IED with a healthy IED link → the SCADA server connection is down; control quality flows server→client by design.
  • Tag Processor compiles but a row does nothing → check the exclamation-mark rows and the Code tab; enable Treat Code not Generated as Error to make these fatal.
  • Everything is slow → task overrun. Compare the overall task timer to the cycle time (need ≥140% headroom); watch CPU_Burden_Percent.
  • Autocompleted name looks different in OPC UA / flattened contexts → some interfaces flatten periods to underscores (GlobalVars_SystemTags_CPU_Burden_Percent_stVal) — same tag, different spelling.
