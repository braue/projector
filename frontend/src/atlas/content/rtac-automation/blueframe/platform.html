☰The rules, stated plainly

Platform

  • Enter a device once. Blueframe's central idea is smart shared data: IEDs, connections, and users are defined once in the management tools, and every application subscribes to what it needs.
  • Resource Management is where everything starts. No DMA plan, no FLISR feeder, and no protocol client works until the device exists there with a working connection.
  • Blueframe ships with no user accounts. The first login creates the initial administrator; there is no default password to change because there is no default user.
  • Two independent access lists govern who sees what. Resource Access Lists control resource visibility; Profile Access Lists control who may modify profiles and redeploy their instances. A role assigned both gets the superset.
  • Only ports 443 and 80 are open by default (80 redirects to 443). Applications open their own ports — check each application's manual.
  • Everything is containerized and versioned. Import a package, then choose which version to install; uninstalling a package permanently deletes its configuration and stored data.

1What Blueframe is, and what runs it

Blueframe is an embedded, modular, container-based application platform designed to operate in a secured environment. Hardware (or a virtual machine) sits at the bottom; a hardened Linux-based operating system with measures such as allowlisting sits on top of it; the Blueframe application platform and its containerized applications sit on top of that. Every application and tool is reached through a secure web environment — there is no desktop client to distribute.

First boot

  • Blueframe ships without default user accounts. On first access you create an initial administrator, which Blueframe automatically assigns to the admin role — the permissions needed to create every other user and role.
  • The Portal then shows the installed applications, including the system-management ones. The Application Launcher in the top-left sorts by category or alphabetically with a search box; system tools live under the System category.
  • The Application Bar carries quick-links to Alarms and Notifications generated by any installed application, regardless of which one is open, plus Help.
  • The User Profile badge sets per-user preferences: landing page, password change, light/dark theme, and whether the favorites bar is visible (default: visible).
  • On Automation Platform hardware, a password jumper allows creating a temporary user to manage accounts, and a master reset jumper resets to factory settings on every restart while enabled. Neither exists in a virtual environment — there is no way to bypass the password requirement there.

2Resource Management — define the device once

A resource is anything Blueframe talks to: an RTAC, relay, meter, switch, or other IED, and also a remote database or another Blueframe node. Define it once here and every application uses it; change it here and the change permeates the system.

3Engineering access, sessions, and access lists

Four role-permission scenarios are documented, from view-only through full administrative access; the pivot in each is which of these two lists the role is on. (Animated in the browser.)

Sessions and Direct Resource Access

  • A session is a terminal or web-proxy path to one resource, built on one of that resource's connections and tied to specific role access. Each session supports an allowlist and a denylist of commands, plus command aliases — useful for sending escape characters or giving users one consistent command across many device types.
  • Access Level permissions take precedence over allowlist and denylist entries.
  • Optional SSH access on terminal sessions issues a single-use password for proxy access to the device each time the session is connected in Direct Resource Access.
  • File read and write are supported on connection types including SEL over Telnet and SEL with FTP. To write, a user needs both the Can Write permission and Access Level 2 on the session.
  • Quick Connect lets privileged roles open an ad-hoc terminal by entering a session name, protocol, host, and port. That connection disappears on navigating away from Direct Resource Access.
  • Last-session logs are available from the ellipsis beside a disconnected session — the first place to look when a session will not establish.

Engineering Access Policy

Rather than configuring an engineering-access session on every resource, define one policy and apply it across many connections. Setup:

  1. Configure the resource's connection with a supported protocol — SEL-3620 SSH/TCP/Telnet, SEL (TCP, Telnet, SSH, or Client Serial), TELNET, SSH, TCP, or TERMINALGATEWAY — and enable Engineering Access on it.
  2. Go to Resource Management → System → Admin Settings → Engineering Access and select New Policy.
  3. Name the policy, pick its type, and decide whether it activates on creation.
  4. Select the roles and access levels the policy grants.
  5. Choose the SSH password prompt, the file access type, and whether SSH access is enabled.
  6. Optionally configure aliases, allowlists, and denylists, then Create.
Policy permissions alone do not grant access. The resource must also be in a Resource Access List or Profile Access List associated with the role, or users in that role cannot reach the device no matter what the policy says. Policy and session permissions are independent: a role with session permissions can use Direct Resource Access even with no Engineering Access configured, and when both exist, separate sessions appear, each enforcing its own permissions at the highest configured access level. The admin role has implicit read and write on all sessions.

Parent/Child Navigation Lock applies these permissions to hierarchies. Where an RTAC resource has child devices, access to the parent does not implicitly grant access to children, and vice versa — blocking unauthorized navigation with <Ctrl+D> and POR X during a direct-access session.

Verify the result with System → Reports → Engineering Access Report, which can be generated by resource or by role.

4Protocol Services

Protocol Services configures communications ingress (client) and egress (server): data concentration among IEDs and protocol conversion for upstream SCADA, HMI, or other polling devices.

Building a service

  1. Add a client or a server. A client can be associated with a resource from Resource Management; matching connections then appear in a dropdown, and selecting one imports the connection settings automatically and makes the Connection Type read-only. Optionally inherit the resource's name.
  2. New services start as a Draft. Edited settings show an asterisk and a bold highlight; a warning icon indicates the draft differs from the deployed service.
  3. Deploy creates and starts the service. Its state becomes Comms Online or Comms Offline; a stopped service reads Stopped. A service cannot be deleted until it is stopped.
  4. Editing a deployed service creates a draft. Unsaved changes are lost on navigating away; saved drafts persist until deployed or deleted, and the Service State Selector switches between draft and deployed.
  5. Settings export in JSON from the toolbar ellipsis, and can be edited and imported back into an existing draft.

DNP3 specifics

  • Client points are added per DNP3 object tab — specify a starting index and quantity. The service must be in draft state to add or delete points. Binary Outputs carry extra columns for Control Model and pulse behavior.
  • Server points reference client, application, or system points rather than owning them: Point Type and Publication Subject are inherited and read-only. Drag points from the Data Points panel onto the map; they append sequentially, and the Point Number (index) is editable and must be unique per object.
  • Server extras: Var Obj columns set the variation returned per object, Event Class groups data for reporting, Binary Inputs can be inverted, and Analog Inputs carry scaling and deadband columns. SEL does not recommend a deadband of 0 on any analog point.
  • Server sessions: up to 20 simultaneous client connections, each with unique event and acknowledgement buffers. Setting Allow Anonymous DNP/IP Clients to TRUE accepts only one connection with a shared event buffer, and a new client terminates the previous one.
  • Diagnostics tab on deployed services shows real-time communications status, message statistics, and a history of status changes and errors.

The protocol itself is covered on DNP3 Fundamentals; the integration discipline is on SCADA Integration.

ICCP client

Blueframe includes an IEC 60870-6 TASE.2 (ICCP) client, compatible with Blueframe OS 2.0.x and later, supporting control blocks 1 (polling), 2 (transfer sets), and 5 (control).

  • Capacity: up to 100 client connections; 10,000 status points per connection and 100,000 across all connections; 1,000 control points per connection and 10,000 across all.
  • Configured by JSON file uploaded to the application and validated immediately, with errors returned in the import window.
  • Each data point needs a fully qualified ICCP name in domain/object format, an ICCP data type (the Data_State, Data_Discrete, and Data_Real families with their Q, Timestamp, and Extended variants), and a Measurement Point/Quantity pair that must be unique across the whole signal hub.
  • Control points add a per-point Select Before Operate flag that must match the server's configuration.
  • No security or authentication features from IEC 60870-5-6, and no support for discovery services or creating datasets on the server.

5Identity, notifications, and viewers

Identity and Access Management

  • Roles carry the permissions; users inherit them. A user can hold several roles, and the role with the broadest permissions wins.
  • Each application exposes Can Launch and Can Manage permissions per role, plus application-specific advanced permissions.
  • Accounts support an activation date and an expiration. Logging in before activation is denied; after expiration authentication fails, though active sessions continue until logout.
  • Password policy is administrator-defined and enforced at creation, with a live message showing which requirements are unmet. Blueframe requires 6–30 characters, stores only a one-way hash, and can force a reset at next login.
  • The default admin role cannot be deleted, and some of its permissions cannot be revised — deliberately, to prevent losing the permissions needed to configure the system.
  • Central authentication is supported: LDAP, RADIUS, and single sign-on.

Notifications

  • Blueframe emails data from supporting applications through an SMTP server.
  • An SMTP server connection must exist in Resource Management first.
  • Then in Notifications, create a Recipient Group: choose the SMTP server resource, specify a valid sending address, and add recipient addresses.
  • Supporting applications are then configured to send to that group — DMA publishing uses this for email endpoints.

Data Viewer

  • Near-real-time status of any data shared across the platform — every Protocol Services client and server point is visible.
  • Live value updates, saved reports, custom filters and watchlists.
  • The fastest way to prove a point is arriving before blaming the application above it.

Resource Viewer

  • A dashboard of near-real-time status for assets defined in Resource Management once communications are configured. Tree view mirrors the Resource Management folder structure; a grid in the centre supports search, filter, resize, reorder, and sort; a details pane on the right updates live.
  • Requires labels. Only resources with a valid label and a supported model type appear — SEL RTACs require the label rtac, case sensitive. Folders with no valid entries show as unavailable.
  • RTAC HMI panel (Resource Viewer 1.7.0 and later) renders an RTAC's HMI inside Blueframe. Requirements: the resource labeled rtac, an HTTPS connection with RTAC credentials that have the right RTAC permissions, and the RTAC HMI license on the RTAC — without it the diagrams will not load.
  • Not supported in the HMI panel: trend groups and static trends, dynamic trends, full-screen HMI display, and RTAC project info. The HMI SOE viewer and alarm viewer can be added as separate panels.
  • Permissions compose: Can Manage is required to issue controls from the HMI panel, Can Launch gives read access, and all RTAC account permissions are enforced on top of the Blueframe ones.

6Application Management

Installation is package distribution: import a prepackaged application into Blueframe, then deploy the version you want. Importing is not installing.

  • The Dependencies tab lists each dependency for a version, its currently installed version, and the minimum required version. Different versions of the same application may have different requirements.
  • Licensing comes two ways: a preconfigured Blueframe machine with everything preloaded, or a license file loaded through System Management before uploading and installing the package. Updating an existing package does not require reloading its license.

7System Management and logging

System Management

  • Status — CPU and memory performance, network interface I/O, storage disk I/O. Detailed metrics are kept seven days or 10 GB, whichever comes first, and export as a compressed tsdb file.
  • Device — system name and a quick-identification colour (web-interface identity only; it does not change the hostname), date and time settings, power options, and factory reset. Blueframe stores all timestamps in UTC.
  • Network Settings — interfaces, host parameters, and the hostname used as the syslog message source.
  • Packet Analysis — capture and analyze network traffic from the box.
  • Certificates — X.509 management. Blueframe uses a self-signed certificate by default, which browsers will warn about; download a CSR, have it signed, and upload the result, or add Blueframe's certificate to the external system's trust store.

System Logs

  • Security logging — login and logout attempts, account changes, session errors — in a filterable grid. Separate permissions to access logs and to manage them (policy changes and deletion).
  • Filters can be saved and survive power cycles and OS upgrades; each column supports multiple criteria.
  • Display in local or UTC time, with live table updates that can be paused or permanently disabled.
  • Anti-chatter: if an application logs the same message type more than a set number of times inside a window, Blueframe removes those entries and writes one record noting the filter applied.
  • Retention is by days or by disk utilization. A log entry is roughly 200–600 bytes (about 450 typical), so one MB holds around 2,300 logs. Removal happens 1,000 entries at a time; the day limit is checked every 12 hours and disk utilization every 10 minutes.
  • Syslog forwarding in RFC 5424 format (receiving either RFC 3164 or 5424), 1024-byte packets, facility fixed at 16, severities 128 Emergency through 135 Debug. Timestamps come from the originating host — so accurate time synchronization is what makes correlation possible.
Ports: by default only 443 and 80 are open (80 redirects to 443, and web access is HTTPS only). Applications open their own ports for their functionality — DMA listening uses 5000, and the RTAC PostgreSQL connection it opens in response uses 5432.

8Gotchas

  • Profile changes do not reach deployed instances. They apply only to newly deployed ones; to update existing instances you must un-deploy and re-deploy them.
  • A resource needs the right connection for the job. Multiple connection paths to one resource are supported precisely because some data is only reachable over a specific protocol — RTAC properties over PostgreSQL, RTAC settings over HTTPS.
  • Child resources need a globalDeviceId configured before they can be added to a parent COMPROC, POSTGRESQL, or SEL-3620 SSH connection.
  • Sessions may not appear at all unless Connection Services 1.18.0 or newer is installed — otherwise they only become configurable once the Resource Communication Services package is present.
  • Resource Viewer silently ignores unlabeled resources. The rtac label is case sensitive.
  • Anonymous DNP3 server mode is single-client. Enabling it to "make things work" quietly caps you at one connection with a shared event buffer, and each new client kicks off the last.
  • Uninstalling a package destroys its data. Export first if there is any chance you want it back.
  • The self-signed certificate stays until you replace it. Every user learns to click through the browser warning, which is exactly the habit you do not want — see Substation Cybersecurity.
