☰The rules, stated plainly

RTAC security

  • There are two separate account schemes: accounts in the ACSELERATOR RTAC software database on your PC, and accounts on the RTAC box itself. Securing one does nothing for the other.
  • The box ships with no user accounts — the first web login creates the first administrator. Forget it and the only way back in is the factory-reset jumper.
  • Since firmware R141, access is permission-based: default roles are bundles of permissions, and you can build custom roles. Project download, HMI controls, and web viewing are each gated by different permissions.
  • LDAP checks happen only for users without a local account — local accounts always authenticate locally, which is your fallback if the directory dies.
  • Every login/logout is logged by default; add a syslog destination and the box streams security events to your collector.

1Two account schemes (don't confuse them)

The SEL-5033 manual is explicit: the RTAC system has two account schemes, plus stored passwords for protocol sessions. Mixing them up is the classic source of "but I changed the password" confusion.

ACSELERATOR software accountsLive in the local project database on your PC. Gate who can open, create, and send projects. Ship with defaults admin/TAIL and engineer/OTTER.
RTAC box accountsCreated in the RTAC web interface. Gate the web UI, HMI, ODBC/database access, and transparent connections. None exist from the factory.
Protocol passwordsCredentials the RTAC uses toward IEDs and masters. Encrypted in project versions R136+; shown as asterisks in the software.
  • Software side: both default roles can create/delete projects and send/read projects to/from RTACs; only Administrator can create/delete user accounts and unlock projects locked by an improper close. SEL says change the defaults immediately — the software nags with a "database is not secure" warning until you do. You can't delete or disable the account you're logged in with, so one administrator always survives.
  • Software passwords must be strong: minimum eight characters with at least one digit, one special character, one uppercase, and one lowercase. Project passwords follow the same rules.

2First login & password rules on the box

Out of the factory the RTAC has no defined user accounts and no default service accounts. On the first HTTPS connection to the web interface, the landing page prompts for a username and a password (entered twice) — that pair becomes the first administrator on the box.

  • The first-login password must be complex: 8–72 characters with at least one number, one lowercase, one uppercase, and one special character.
  • If you lose it, you're locked out. Recovery is internal jumpers per the Factory Reset section of the hardware manual — a site visit, not a phone call.
  • For accounts created later: usernames are 7-bit printable ASCII excluding @ # $ % ^ & + = { } [ ] : ; " ' , < > ? \ and spaces; passwords accept any 7-bit printable ASCII. Complex passwords follow the same 4-class rule; the name diag is reserved by an internal application. From R141, an account can no longer share a name with a role (an upgrading Administrator account becomes Administrator_).
  • Password history (R149+): the Password History Count dashboard setting (0–24, default 0 = off) blocks reuse of that many previous passwords.
  • Accounts can be given an expiration date/time or disabled while still existing; SEL's guidance is to keep at least one Administrator account that does not expire.
  • A configurable usage policy banner is always displayed before credentials are entered, on both the local and web interfaces.

Sending a project also sends security settings. ACSELERATOR RTAC pushes User Accounts and LDAP settings with a project only if the logged-in box account holds Account Write; Ethernet/Hosts settings ride on Network Write; certificates and SSH keys ride on Security Write. A project send by an Engineer-role account silently skips the account payload.

4Central authentication: LDAP (and RADIUS)

The RTAC authenticates role-based accounts against Active Directory using LDAP. The order matters: when a user without a local account requests access, the RTAC polls the central directory to verify authorization; local accounts never leave the box. LDAP binds use STARTTLS with X.509 certificates — the root CA of the LDAP server's chain must be installed on the RTAC (base64 .cer only; binary formats unsupported), or binds fail.

Central login with a failed-bind branch: no local account → server 1 bind fails → server 2 answers → LDAP group maps to an RTAC role → session granted. ▶ Animated in the HTML edition.

  • Service-account risk: if the bind service account is revoked or its password expires, the RTAC can't reach LDAP and all centralized users are locked out. Local accounts keep working — keep at least one local admin.
  • Deleting an LDAP user in the accounts list does nothing. Users who logged in via LDAP appear in the local accounts list, but their access is managed on the LDAP server.
  • Configuring LDAP needs Account Write + Network Write + Security Write on the account doing the work.
  • RADIUS is the alternative: primary/backup server, UDP port 1024–65534, shared secret, PAP / EAP-PEAPv0-MSCHAPv2 / EAP-TTLS-PAP; a downloadable SEL RADIUS dictionary defines the vendor-specific attributes that carry the role, and the settings page has a test-credentials button.

SEL reuses the blank-LDAP-form idea across products — the SEL-3373/SEL-5073 PDC forms ask for the same core fields (Search Base DN, Bind DN, User Filter, Group Attribute, group→role mappings).

5Security logging & syslog

The RTAC ships with User_Logged_On and User_Logged_Off logging enabled by default in the Tag Processor, and exposes ten User Sessions system tags for user activity. Every log entry auto-generates a status bit you can map like any digital point — the manual's worked example pulses the alarm contact (OUT101) on every login. From R147, login SOE messages include the source IP address.

  • Security events are stored in nonvolatile memory — 30,000 to 500,000 events depending on hardware, oldest overwritten first. Deleting all SOE logs itself creates a time-stamped log naming the user who did it.
  • Syslog (RFC 3164) forwarding: web interface → Network → Syslog → Add Syslog Destination → server IP + threshold. Multiple destinations are supported; the RTAC buffers up to 10,000 syslog messages.
  • Format: PRI = Facility × 8 + Severity with the RTAC facility fixed at 23. Severity comes from the Tag Processor's case-sensitive Logging Priority string — Emergency 0, Alert 1, Critical 2, Error 3, Warning 4, Notice 5, Informational 6, Debug 7; anything that doesn't match exactly becomes 6. The threshold sends everything at or above the chosen priority.
  • Example from the manual: <190>Mar 21 2015 12:10:08 SEL-3530-xxxxxx RTAC Logger: … Informational, Security, SystemTags.User_Logged_On, 'SEL logged on device via Web'.
  • Timestamps ride the originating host's clock — keep the RTAC time-synced or your collector's event correlation is fiction.
What gets a security log: logins/logouts (with IP), settings and project activity, SOE deletions, DoS-monitor messages (Impending watchdog failure; adjusting system priorities), plus anything you log yourself by enabling logging on a Tag Processor variable with a Security category.

6Hardening the box

The RTAC runs a stateful, deny-by-default firewall: ports open only because configuration opens them. Hardening is mostly a matter of not enabling what you don't need.

Factory defaults: web + database access enabled on mainboard Ethernet only (PCI-expansion ports deselected); ping response, DHCP, IPv6 all disabled; HTTP→HTTPS redirect disabled, so browsers must type https://.

  • SEL's own short list (Appendix E): enable web and database access on only the interfaces that need them; don't remove the default SystemTags logging; keep firmware current. Also: don't set unused Ethernet ports to an active subnet.
  • Sessions: Web Session Time-out 0–720 min of inactivity (0 = never — and then the HMI stays open for controls without re-authenticating; avoid). HMI Read-Only Mode drops an idle HMI to view-only and demands login for any control — the sane wall-display posture.
  • Engineering access: tunneled serial/engineering channels support SSH or SSL/TLS; SSH drops the connection after three failed attempts, and key-based auth is managed on the web interface's SSH Keys page. Project download and ODBC ride TLS.
  • Certificates: the factory X.509 is unsigned/self-signed — generate a real one (Common Name must exactly match the address you browse to, SAN populated) and have your CA sign it. CA certs installed on the box also serve LDAP and TLS tunnel validation.
  • URL whitelist (R143+) restricts which external webservers the RTAC web UI can navigate to; restricted BIOS (R151+ on x86 models) and digitally signed firmware close the platform itself. No extra software can be installed on an RTAC.

Substation-wide architecture — gateways, DMZs, and where the RTAC sits in the larger security zones — is covered in the networking cybersecurity page in atlas.

7Protecting the configuration itself

  • Project passwords (R136+): right-click a project → Set Password (or Ctrl+L in an open project). The project won't open without it; status shows Password On. Disabling requires the current password. Same strong-password rules as user accounts.
  • Export encryption: every exported project is encrypted with a default hidden passphrase; enable Prompt for passphrase to encrypt project export to set your own. The passphrase is asked on import — after import, it's no longer needed to open the project.
  • Protocol passwords: plain text before project version R136, encrypted from R136 on (shown as asterisks). Converting a project encrypts them. From firmware R150, a project download/activation offers a true/false choice: use the project's protocol passwords or keep the ones already on the RTAC.
  • Password report (R141+): an Administrator (or an account with the password-report permission) can pull a CSV of every IED password in the active configuration from the web interface — it never includes RTAC user-account passwords. The Device Password Read permission gates the equivalent API access.
  • Backups: the running project downloads from the dashboard as an encrypted .exp; a full database backup zips every project plus the connection directory and managed passwords.

8Operational practice & gotchas

  • Change the software defaults first. admin/TAIL and engineer/OTTER are printed in every manual and application guide on the planet. SEL: change default usernames and passwords immediately, before deploying.
  • Per-user accounts, not shared ones. The cybersecurity appendix's rationale: user-based accounts increase logging granularity and give auditable, non-repudiable tracking of who did what. A shared login turns the SOE trail into "somebody."
  • Lifecycle: use expiration dates for contractors, and disable rather than delete accounts you might need again (AG2015-23's recommendation) — but remember disabling an LDAP-listed user changes nothing until the directory says so.
  • Don't let the last admin expire. Configure at least one Administrator account with no expiration; the software refuses to delete/disable the account you're logged in with for the same reason.
  • Factory reset is the only password recovery. Jumpers wipe programming, accounts, and logs — treat the first-admin credentials like a protection settings sheet.
  • Decommissioning: factory-reset from the Device Management page (or the jumper procedure) to purge configuration; a reset erases all certificates except the default unsigned one.
