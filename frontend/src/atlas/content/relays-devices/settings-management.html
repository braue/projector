Settings Management

☰The rules, stated plainly

Settings discipline

  • The relay is the authority, the archive is the record, and they must agree. If you cannot prove they agree, you do not know what is protecting the feeder.
  • Every visit produces an as-found and an as-left, even when nothing changed. “No change” is a finding worth having on file.
  • A setting has a reason. Record it. The fault study, the coordination requirement, or the standard that produced the number is more valuable than the number.
  • Settings changes get reviewed by someone who did not write them. The cost of a second pair of eyes is far below the cost of a misoperation.
  • Read back what you sent. The file you intended to send and the file that is in the relay are different objects until you have proven otherwise.
  • Templates enforce the standard; free-form editing lets every relay drift into its own dialect.

Keep a text export next to every binary file. Binary settings databases are readable only by a compatible version of the tool. A plain text export can be diffed against the next revision, searched for a value across the whole fleet, and read by anyone. Doing both costs seconds.

3Naming and versioning

File naming

Name by fact so the file sorts and searches usefully:

SITE_DEVICE_YYYYMMDD_asfound.rdb
SITE_DEVICE_YYYYMMDD_asleft.rdb
SITE_DEVICE_YYYYMMDD_asleft.txt
SITE_DEVICE_YYYYMMDD_basis.md
  • Site and device tag exactly as they appear on the one-line and in SCADA — not a nickname.
  • ISO date so files sort chronologically.
  • The words asfound and asleft, never “final”, “new”, or “v2”.

Version control

  • A real version-control system beats a shared folder: it records who changed what, when, and why, and it makes the diff trivial.
  • Commit the text export so diffs are meaningful; keep the binary alongside.
  • The commit message is the change note: “FDR 3: raised 51P TD 2.0 → 2.5 to coordinate with new recloser R-14 per study 2026-08-14.”
  • Tag the state that was actually commissioned, so “what is in the field right now” is answerable without a site visit.
  • Where a formal system is not available, the same discipline applies with dated folders — it is just more manual.

4Templates and standardization

A fleet of relays set individually by different engineers becomes a fleet of one-off configurations that nobody can safely maintain. Templates are the antidote.

  • Design Templates in QuickSet let an engineer lock down most of a settings file and expose only the fields that legitimately vary per application — CT ratio, pickups, addresses. Field staff fill in the blanks; nobody rewrites the logic.
  • What to template: SELogic trip and close equations, target LED assignments, SER trigger lists, port configuration, protocol maps, front-panel labels. These are standard-driven, not site-driven.
  • What to leave open: ratios, pickups, time dials, addresses, device names — the genuinely per-installation values.
  • Version the template itself. When the standard changes, you need to know which relays were built from which template revision.
  • Templates make review cheap. Reviewing a filled-in template is a matter of checking a dozen values; reviewing a free-form settings file means reading all of it.
The real value of a template is what it prevents. Not the time saved entering settings — the trip equation someone rewrote at 2 a.m. that omitted a permissive, the SER trigger list that never included the new element, the target LED that still says what the previous relay's did. Standardization is a protection measure.

Map the active group as a SCADA analog. It is one point, it costs nothing, and it turns “which settings are actually running?” from a site visit into a glance. Alarm any group other than the normal one.

6The change workflow

  1. Establish the need in writing. A coordination study result, a misoperation report, a new device downstream, a standards update.
  2. Retrieve the current settings from the relay — not from the archive. The archive is what should be there.
  3. Make the change in the file, based on the template if one exists, and update the basis document in the same edit.
  4. Diff it. Compare old and new text exports and confirm that only the intended settings changed. Tools change things you did not ask for — a driver upgrade can rewrite defaults.
  5. Review. Someone else checks the diff against the basis. Protection changes deserve a formal approval step.
  6. Send it, during an approved window, with the consequences understood — a settings change may momentarily disable protection and will clear some records.
  7. Read back and verify. Retrieve settings from the relay and diff against what you intended to send. This is the step people skip and the step that catches partial sends.
  8. Test what changed. A pickup change means an injection test at the new pickup. A logic change means proving the logic.
  9. Archive the as-left, the diff, the basis, and the test record, and update the drawings and points list if either was affected.
Retrieve events before changing settings. A settings change clears some record buffers on many relays. If the reason you are there is a misoperation, capture the evidence first — see Event Analysis.

7Fleet-wide changes

Changing one setting across two hundred relays is a different problem from changing one relay. It is where scripting pays and where mistakes multiply.

  • Search the fleet first. With text exports under version control, finding every relay whose 50P1P is below a threshold is a grep, not a survey.
  • Pilot on one device, in a low-consequence location, and prove the whole workflow including read-back and test.
  • Batch by identical model and firmware. A change that is safe on one FID may not exist on another.
  • Stage the rollout so a systematic error affects a few devices, not all of them, before anyone notices.
  • Keep a per-device record of which relays received the change and which are pending. “We did most of them” is not a defensible state.
  • Watch for the ones that are different. Every fleet has a handful of relays that are not like the others — older firmware, different option, non-standard application. They are exactly where a bulk change goes wrong.

8Gotchas

  • The archive and the relay disagree, and nobody knows which is right. Fix it by reading the relay, archiving that as a new as-found, and investigating the difference — not by overwriting the relay with the archive.
  • Sending a settings file built for a different firmware. QuickSet's driver check exists for a reason; overriding it produces missing or defaulted settings.
  • A partial send that reported success. Always read back. This is the single most valuable habit on this page.
  • Nominal current mismatch. A 5 A file into a 1 A relay is a factor-of-five error that looks completely ordinary in the file.
  • Logic changed by a group change. On most relays the SELogic equations belong to the settings group. Switching groups switches the logic too — verify both.
  • Undocumented field changes. Somebody adjusted a pickup during a callout and told no one. Periodic fleet audits — read the relays, diff against the archive — catch this.
  • Points list not updated with the settings. Adding an element without adding its Relay Word bit to the map means the new protection is invisible to SCADA.
  • The basis document written afterward, from the file. That is a description, not a basis. Write it while you are making the decisions.
