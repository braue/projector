Enabling, arming, resets and startup

The chain of conditions that decides whether the DAC is allowed to act, scheme-wide and per feeder.

§02DA Lib / DA Adapter 105.0.2Code-derived

The rules, stated plainly

  1. AR runs only when Enable AND this DAC is the active redundant DAC AND the library is licensed (licensing) AND there is no settings error.
  2. A feeder is Armed when AR is enabled AND the feeder is not Excluded AND not Excluded by underfrequency. An unarmed feeder detects nothing and is never used as an alternate.
  3. An armed feeder that is Abnormal is still armed, but with the default abnormal mode (None) it can neither isolate nor restore and cannot be an alternate source.
  4. A system Reset is ignored while any DA sequence is in progress. When accepted it re-initialises the whole model.
  5. Outputs and commands are suppressed for the first 5 s after any reset (MapOutputs).

Feature enables

Miscoordination detection, open-phase detection, overload detection, load shed and loss-of-source detection each have a setting default and an optional SCADA Enable/Disable pair. A feature is SCADA-controllable only if both its enable and its disable points are mapped; otherwise it is forced to the setting default every scan. Each feature enable is ANDed with AR_Enabled inside the manager, so turning AR off turns them all off. ADP/DA_CONTROL.prv_ControlInputs

Overload detection and load shed are additionally forced off whenever any DA_CONNECTOR is in service (g_DA_ConnectorInService), because the solver cannot handle overload transfers across DAC boundaries. OBJ/DA_MANAGER_AR

Licensing

The library checks what this RTAC is licensed for and turns that into two permissions: AR permitted (fault isolation and restoration) and DFO permitted (voltage/var optimisation). Each permission has a feeder limit. The check reads only the RTAC itself, through its part number (MOT) and its installed license strings. Nothing in the DAC settings changes it. _zMOTCheck/prv_LicenseLimits _zMOTCheck/prvfb_LicenseManager OBJ/DA_CONTROLLER

The rules, stated plainly

  1. The license is read once, at startup. A second attempt runs on the Adapter's first scan in case the OS call failed during init. After that it is never read again, so a new license or a new part number takes effect only after a restart.
  2. The DAC uses the first of these four checks that gives a result: an all-features part number, then feeder-count license strings, then a legacy part-number code, then a demo license.
  3. AR is permitted when the licensed AR feeder count is above 0 and the number of feeders configured on this RTAC does not exceed it. Going over the limit does not just drop the extra feeders. AR is turned off for the whole RTAC.
  4. Without the AR permission, the manager's Licensed output is FALSE, so AR_Enabled is FALSE. The effect is the same as Disable: no feeder is armed and nothing is detected or commanded.
  5. DFO is judged separately, with its own count and limit.

What counts as a feeder

  • AR count: the global FeederCount. This is the highest feeder slot assigned on this RTAC across all schemes. Every DA_CIRCUIT takes a slot, and so does every DA_CONNECTOR, because each connector builds a feeder to stand in for the neighbouring DAC's side. Feeder/Assignment/mFEEDER_Assign
  • DFO count: the circuits running voltage optimisation (PermitOp TRUE and PermitLoop FALSE), counted again every scan. OBJ/DA_CIRCUIT.prv_VVO
Interpretation Connectors use up license slots. A 20-feeder license on a DAC with 18 circuits and 3 connectors comes to 21 slots, which exceeds the limit and disables AR completely. Count connectors when sizing a license.

Demo / lab license

  • When Demo is set, a 4-hour timer starts the first time the controller runs. When it expires, DemoOver latches TRUE and clears only on a restart or power cycle.
  • DFO honours this: g_DFO_Enable requires (Licensed OR Demo) AND NOT DemoOver. OBJ/DA_MANAGER_OP
  • AR does not check DemoOver. Demo mode sets the AR count to 100, so AR_Permitted stays TRUE after the 4 hours as well. See the caveat below.

Startup timeline

  • Scans 1–3: Startup TRUE; everything initialises.
  • Cycles to 10: indexes assigned; at cycle 10 a topology checksum is taken (used to keep calibrated DFO X-factors only if the topology is unchanged); from cycle 10 the circuit-zone and load-allocation validators run (ZoneWithZeroLoadAllocation settings error).
  • Every comm device gets a poll request on its first scan; the integrity poll also fires on DA enable.
  • Adapter: 10 s start-up delay; without a redundancy/setpoint library, the DAC is marked active and operator setpoints initialise to defaults at the end of it.
  • MapOutputs goes TRUE 5 s after the controller reset ends; until then, no command or feeder status output is written.
