What is sourced, what is inferred, and how to verify anything here against the code.

§00DA Lib / DA Adapter 105.0.1.100Code-derived
  • Body text is code-derived. Every rule was read out of the Structured Text. Where a rule lives, a small grey tag such as Feeder/FEEDER names the POU. Paths without a prefix are under DA Lib/POUs/POUs/DA_INTERNAL_USE_ONLY/. OBJ/… means DA Lib/…/DA_OBJECTS_AR/. ADP/… means DA Adapter/POUs/….
  • Interpretation Notes with a dashed line mark where I explain intent or field consequence that the code implies but does not state.
  • Code caveat Notes like this mark places where the code looks wrong, contradicts its own comments, or has a surprising side effect. Treat these as leads to confirm on a test set, not as settled fact.
  • Two sets of defaults exist. The DA Lib blocks (DA_MANAGER_AR, DA_SCHEME) have one set of pin defaults; the Adapter's DA_CONTROL passes a different set. Projects built on the Adapter get the Adapter defaults. §20 lists both side by side.
  • "Scan" means one execution of the RTAC task. Nearly everything is re-evaluated every scan; very little is a one-shot sequence. That matters: the DAC does not run a script, it keeps re-deciding from the present state.
  • To search the code yourself: grep works directly on the XML because the code sits in plain CDATA blocks. Blocks talk to each other through global arrays and flags (dEQUIPMENT, dFEEDER, dNODE, DA_EVENT_*, BestSolution), not through calls, so follow a flag by grepping for its writers and readers.
