The event sequence

How a disturbance moves from detection to a finished reconfiguration. Each feeder runs its own small state machine; the manager coordinates them and owns the solve and execute steps.

§03DA Lib / DA Adapter 105.0.1.100Code-derived

The rules, stated plainly

  1. A new event (trip, open phase, overload trigger, source event, remote event, bus restore) moves the feeder from IDLE to UPDATE and polls every device on the feeder plus feeders within TransferDepth.
  2. UPDATE ends when every on-scan device on the feeder has answered AND MinimumUpdateTime has passed. A device that never answers ends UPDATE at the timeout with AbnormalCondition and no restoration.
  3. ANALYZE confirms the event (lockout found, open phase persisted, etc.). The feeder returns to IDLE when confirmed with no unresolved faults and adjacent feeders updated, when the event disappears, when AnalyzeTimeLimit expires, or when the fault is shown to be off the feeder.
  4. The manager solves only when every feeder is idle (or sitting in ANALYZE with a confirmed event). One solution covers all confirmed events at once.
  5. Execution is re-evaluated every scan until all opens/closes are done or ReconfigTimeLimit expires.
  6. Switches needed purely for isolation are opened at confirmation time, before the solve, when allowed.

Per-feeder state machine

new event, RTN or update request IDLE ───────────────────────────────────▶ UPDATE ▲ │ latched and all devices updated │ update timeout or nothing latched ▼ ├───────────────────────────────────── ANALYZE │ confirmed with no unresolved faults, │ └── or event gone, timeout, off feeder ◀───┘

UPDATE polls the feeder and its neighbours; leaving UPDATE needs MinimumUpdateTime elapsed. An update timeout with an event latched sets AbnormalCondition. ANALYZE exits on: confirmed with NumUnresolved = 0 and adjacent feeders updated; event no longer latched; AnalyzeTimeLimit; or Fault.OffFeeder.

Feeder/FEEDER ExternalHelpers/Feeder/mFEEDER_RefreshStep

While IDLE, the feeder rebuilds its actual and normal topology each scan, but only when there is no fault, no source or remote event, no switch opened in the last 10 s (FaultDetectorDelayTime), no confirmed event, and no collaboration step other than Execution. This freezes the picture of the feeder while an event is being worked.

Detection and confirmation, event by event

Each scan an ARMED feeder runs mFEEDER_DetectEvent. Event.New is the OR of the new-flags; Event.Latched the OR of the latched flags. Confirmation in ANALYZE follows a fixed priority: source event (with any coincident fault) → fault → remote event → bus restore → open phase → overload. Feeder/Event/mFEEDER_ConfirmEvent

The feeder's overall Event.Confirmed needs: (fault confirmed AND source event confirmed) OR (fault confirmed AND no source event) OR (source event confirmed AND no fault) OR open phase confirmed OR overload confirmed OR (remote confirmed AND no fault) OR bus restore confirmed. On confirmation the feeder sets Reconfiguration.Started, the scheme sets DA_EVENT_Confirmed, and if the feeder's Permissive is FALSE a permissive request is sent.

Event priority side effects: a fault or source event clears any overload and RTN on that feeder; an open phase clears overload and RTN; a remote event clears RTN. A new event while an RTN is being worked wipes every restoration list (the RTN is abandoned).

The manager's sequence

DA_EVENT_Detected ── feeders in UPDATE/ANALYZE ── DA_EVENT_Confirmed │ ▼ AllFeedersIdle (idle, or analysing with event confirmed) DA_Analyze: AbnormalRestoration.Fault.Process() ← isolation around abnormal devices mAR_FindSolution() ← solver, §13 SourceReversal.PrepScenario() │ ▼ SolutionFoundExecution DA_Reconfiguration: g_SolutionExecution.Execute.Run() every scan ← §14 │ ├─ all done (DA_PhaseThreeComplete) ─► DA_EVENT_Complete ─► completion flags, reports └─ ReconfigTimeLimit / abort ─────────► RestorationFail, ExecutionFailure

When the sequence ends (complete, timeout, abort, disable, or nothing left to do) the manager clears DA_EVENT_*, DA_RETURN_*, every equipment Restore, Root and SW.Isolation flag, and every feeder's RTN state. On the rising edge of reconfiguration and on the end of the sequence it clears equipment fault latches (and pulses Fault.Reset to the relays) and clears feeder events. OBJ/DA_MANAGER_AR

DA_InProgress = event detected or confirmed, RTN detected or confirmed, analysing, reconfiguring, or a collaboration active for ≥ 2 s. Many behaviours key off it: Reset is refused, overload detection is suppressed (and for 30 s after), voltage-discrepancy alarms are not raised, watchdog pulses stop, polling speeds up, open-phase disarm timers pause.

Completion flags

When the sequence ends every feeder with Reconfiguration.Started (that is not a pure RTN) gets ReconfigurationComplete (success) or RestorationFail (abort/timeout/insufficient capacity), plus any of:

FlagSet when, at the end of the sequence
VoltageLimitExecution was still waiting for voltage on a source side (DA_SEQ.WaitingForVoltage), or an RTN close lacked Live2.
CommandFailureA command was still in progress (no feedback) when the sequence ended.
AbnormalConditionWaiting for a source, a close-onto-fault happened, a device failed to answer the update, or an RTN found an abnormal/unoperable device.
CapacityLimitThe chosen solution sheds load or leaves a temporary-limit overload (NotEnoughCapacityFound), or an RTN found a source-group mismatch.

These feeder flags persist until a feeder or system reset; ReconfigurationComplete and RestorationFail also self-clear after 10 minutes. OBJ/DA_MANAGER_AR.EventCompletionFlags
