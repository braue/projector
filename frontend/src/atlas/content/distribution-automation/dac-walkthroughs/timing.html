End-to-end timing

How long each stage of an event takes, which timer or condition gates it, and how to tell from the logs where a slow or stalled restoration was waiting.

§26DA Lib / DA Adapter 105.0.1.100Code-derived

The rules, stated plainly

  1. The DAC does not run a stopwatch sequence. Each stage starts as soon as its conditions are true. Total time is protection time + the DAC's minimum waits + communication latency + device operating time.
  2. Only two DAC timers always add time: MinimumUpdateTime (10 s) in UPDATE, and for open phase or loss of source, OpenPhaseConfirmTime (60 s). Every other timer is a limit. It only matters when something is late.
  3. For a permanent fault, most of the elapsed time is the reclosing sequence. The DAC can't confirm the fault until the last shot locks out.
  4. Command feedback is not polled for. CHECK_POLL is FALSE, so the DAC learns a device moved only when the RTAC's normal communication delivers the new status. Slow polling or no unsolicited reporting adds directly to every open and close.
  5. When a limit expires, the result is always a named flag: UpdateStepTimeout, AnalyzeStepTimeout, ReconfigureStepTimeout, CommandFailure or RestorationFail. Each one points to the stage that stalled.

Communication latency, the hidden term

  • Polls during an event: one poll at a time per communication port. A poll that gets no answer times out after 10 s while DA is in progress (30 s otherwise) before the next device on that port is asked. Several silent devices on one port therefore add 10 s each to UPDATE. Communications/DA_COM_LINE
  • Freshness: a device counts as "updated" only when its WatchdogCount changes after the poll request (§04). A relay that answers without incrementing the counter looks silent.
  • Command feedback: a command pulse is 5 s. If the status hasn't changed by the time the 7 s retry timer runs out, a second pulse goes out, then a third. Feedback arrives however the RTAC's DNP client normally gets data. The DAC doesn't trigger a check poll (CHECK_POLL = FALSE).
  • Connectors: polled immediately (no queue). Their watchdog limit is the connector's own UpdateTimeLimit (10 s).
