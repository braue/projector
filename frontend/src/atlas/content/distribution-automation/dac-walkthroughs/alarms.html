Alarms, log entries and diagnostic messages

Everything the libraries write to the RTAC log, raise as an alarm, or send by email. Each entry lists its trigger and whether it stops the DAC.

§28DA Lib / DA Adapter 105.0.2Code-derived

The rules, stated plainly

  1. Every Adapter device block writes change-of-state entries to the RTAC log. The tag reads <device name>: <description> and the message is Asserted or Deasserted. Analog, enumeration and setpoint entries log the new value. The Device Name field is the DAC's logger name.
  2. Only changes are logged. For the first 10 s after startup (StartUpDelayComplete) nothing is logged. The state at that moment becomes the baseline, so a condition already present at startup isn't logged until it changes.
  3. Chatter filter: an entry that changes 5 times within 5 s is suppressed by the RTAC logger (Chatter_Counts_Before_Removal 5, Chatter_Time_For_Removal 5 s).
  4. "DA Alarm" is a category, not an RTAC alarm. Nearly all entries are plain log entries. Only the configuration and licensing entries of DA_CONTROL, the Lib's DA Settings Error entries and the DA Settings Warning start-up entries set the RTAC alarm state.
  5. A settings error disables AR (§02) until the configuration is fixed and resent. A settings warning is informational.
  6. Email alarms are a separate path. They go out only when an emailer is configured, only while the DAC is enabled, and not for devices on excluded feeders.

Settings errors (blocking)

Raised by the Lib's settings error manager. Each one is logged once per POU, 10 s after start-up, in category DA Settings Error with the alarm state set. The scheme's SettingsError output goes TRUE and SettingsErrorText shows the first error in this priority order. AR stays disabled while the error is present. The error list is cleared only on start-up or a controller reset, and then rebuilt from what is still wrong, so after fixing the configuration send it and reset or restart. Email alarms

The Adapter has a built-in emailer. Each buffer collects alarm points. When any point in a buffer has been in its alarm state continuously for 30 s, one email is built listing every point in that buffer that is in alarm. Each alarm is reported once until it clears. Up to 3 recipients. Emails are inhibited while the DAC is disabled (gv_GlobalInhibitEmailAlarms = NOT Enabled) and for devices whose feeder is excluded. An alarm that happened while inhibited is acknowledged silently, so it doesn't fire when the inhibit lifts.
