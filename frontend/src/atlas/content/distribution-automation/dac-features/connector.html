DAC-to-DAC interconnection (DA_CONNECTOR)

Lets a feeder shared between two DACs be restored by either. Each DAC models the other side as a source, a source switch, a line, an edge switch and a boundary line, and the two negotiate a joint solution.

§17DA Lib / DA Adapter 105.0.1.100Code-derived

The rules, stated plainly

  1. The connection is online only when the partner's messages carry a matching library version and its watchdog counter keeps changing.
  2. A watchdog stall of UpdateTimeLimit (10 s on the connector) raises Comm_Alarm and excludes the remote source.
  3. Either DAC can start a collaboration when it has an event or RTN on the shared feeder. Both must accept; either can reject.
  4. Collaboration runs in lock-step phases; each phase completes only when both DACs report it done.
  5. Remote switches are never operated directly: every remote open/close is a handshake request.
  6. Any connector in service disables overload detection and load shed scheme-wide.

Collaboration phases

StateWhat happens
CollabIdleNo joint event. Modelled remote switches track the partner's reported state; remote capacity is mapped from the partner's offer.
InitialUpdateBoth DACs update and confirm their events. Times out after Update + Analyze limits.
InitialSolutionHandshake → InitialSolutionPhase one: each DAC solves alone and publishes what it could give across the boundary (capacity, load to shed, whether restoration is certain).
FinalSolutionHandshake → FinalSolutionPhase two: each solves again using the partner's phase-one offer. Return-close overrides isolation on connector switches here.
ExecutionHandshake → ExecutionBoth execute; remote operations go as handshake commands.
CompleteBoth report execution complete.

Each phase step needs at least 2 fresh watchdog updates from the partner (CON_UpdateCheck). After any abort no new collaboration starts for 60 s. Remote events are mapped onto local feeders only after the connector has been head (local DAC feeds the boundary) or tail (remote feeds it) for 10 s.

What capacity each side sees

The remote source's modelled capacity comes from the partner's published margin, with small floors so the solver never sees zero: OBJ/DA_CONNECTOR.prv_MapCapacity

PhaseLocal feeds the boundary (Head)Remote feeds it (Tail)
FinalSolution / ExecutionHandshakeMAX(remote phase-one capacity, boundary load + 0.1 A)MAX(remote capacity, 0.1 A)
Other phasesMAX(remote capacity, remote tail load + 0.1 A)MAX(remote capacity, 0.1 A)
RTN with zero remote capacity10000 A (unconstrained)

The margin a DAC offers its partner is its node margin if the boundary is fed locally; otherwise the best margin over its open edge switches (minimum of node margin and switch capacity). Connector/Measurements/Current/mCON_getLocalMargin

Interpretation A margin of exactly 0.1 A in a connector report means one side offered nothing (or a clamp to the dead side's margin) and the floor was applied. It is a symptom, not a real measurement.

Outputs

Comm_Alarm, Abnormal, VersionMismatch (partner's DA_Version checksum differs or is 0; connection refused), ControlSequenceFailure (a handshake open/close failed), NoEdgePts (no PTs at the connector edge device), SolutionLoop (both DACs planned to feed the boundary).
