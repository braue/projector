☰The rules, stated plainly

Operating rules

  • Reset is a target reset, not an abort. The only way to stop an event in progress is to disable the DAC.
  • Reset is never required for the next event. The DAC re-arms itself and works the present topology — but an unreset Command Failure or Close-onto-Fault latch sidelines that feeder until someone resets.
  • RTN pushes open points outward, never pulls them in — and it's all-or-nothing: if the whole feeder can't return, nothing moves.

The fine print that bites

  • Fault-indication settings make or break the system: assert on pickup (not operation), never on ground OC alone, never on inrush.
  • A fault indication anywhere on the feeder blocks open-phase evaluation.
  • Command failures and close-onto-fault are latched until a Reset; close-onto-fault aborts the sequence instantly.
  • SEL recommends leaving Load Shed disabled — humans decide to drop customers.

1Operating it: RTN and Reset

Two operator commands, two different jobs: RTN moves switches; Reset clears indications. RTN never clears a target; Reset never operates a device.

The hot-line tags are the procedural guard on step 1: while they are on the bounding devices the feeder is abnormal and RTN is refused — so tags come off last. (Animated in the browser.)

Return to normal

RTN (feeder or scheme) identifies every NC switch now open and NO switch now closed, then hands the reconfiguration sequence the job. It can only push open points out to the feeder's normal extent — a feeder that didn't get the command won't operate its devices to help, so paired transfers need both feeders commanded within a short window (scheme RTN covers everyone). And it's all-or-nothing: if a complete, no-load-dropped path can't be found — capacity, voltage, abnormal tag, a closed normal-open that can't break load, or source groups that forbid the transition — nothing moves at all and CapacityLimit asserts.

RTN before the fault is repaired = close-onto-fault. RTN is rejected while any event is still in progress, but once the sequence has completed, the DAC has no memory that the isolated zone is still faulted — fault indications age out in minutes and a standing FI is not an abnormal condition. An RTN issued before repair will re-energize the zone; protection trips again, Close-onto-Fault detection aborts the sequence immediately, and the latched abnormal (Reset-only) takes the feeder out of play. The procedural guard is the hot-line tags: while they're on the bounding devices the feeder is abnormal and RTN is refused — so tags come off last, and RTN goes out only on confirmed repair completion.

What the Reset command actually resets

Reset controls exist per feeder and system-wide, bound to SCADA points, and are designed to mimic a relay Target Reset. Per the manual, each scope clears:

System-level ResetFeeder-level Reset
Event indicatorsSystem-level indicators (e.g., Permanent Fault Event, Event Failed due to Abnormal Status) and feeder-level indicators (e.g., Feeder Operated due to Permanent Fault Event, Feeder Reconfigured) for all feedersFeeder-level event indicators — the manual lists these as reset "for all feeders" under both commands
Latched device statusesCommand Failure and Close-onto-Fault abnormal statuses, plus "Opened to Isolate Open Phase" targets, for all devicesThe same three, but only for devices within the normal extent of the feeder — if the feeder is extended past its normal tie points, devices beyond them are not reset
Side effectUpdate poll of every device in the systemUpdate poll of devices within the feeder's normal extent

Reset is the primary method of clearing Command Failure and Close-onto-Fault. Incoming resets are ignored while an event is being operated on anywhere in the system, and Reset never stops a sequence — disabling the DAC is the only abort. Separately, a scheme Reset issued while all feeders are idle sends feeders back through the Initialize state, re-evaluating the normal operating arrangement.

Which one do I advise?

  • RTN when the field work is done: fault repaired, locked-out device available again, tags off, comms healthy — any abnormal on the present or normal configuration blocks it. If restoration leaned on a neighbor, command both feeders together (or use scheme RTN), or it will legitimately do nothing.
  • Reset after investigating a Command Failure or Close-onto-Fault — mandatory, it's the only thing that clears them. Until then the feeder is abnormal: blocked from AR, useless as a restoration source, and RTN will refuse. Order: fix the cause → Reset → confirm not abnormal → RTN.
  • Reset as housekeeping: clear event targets after dispatch has reviewed them (the SOE and post-event reports keep the history), or force a fresh poll. Never as a stop button — it's ignored while anything is operating; disabling the DAC is the only abort.

Back-to-back events — no Reset in between

A Reset is not a re-arm switch. When reconfiguration completes, the event sequence returns to Idle with the feeder still Armed, and the next event is evaluated against the present topology — non-normal configuration explicitly has no impact on AR (sequential and concurrent faults are a core capability). What changes for event #2 is the physics: the tie that closed for event #1 is now a loaded closed switch, margins are thinner, and an alternate may already be spent — so the same fault that would have restored fully on a normal system may end in partial restoration or CapacityLimit.

  • The exception is the Reset-only latches. If event #1 left a Command Failure or Close-onto-Fault standing, that feeder is abnormal — a second event on it is confirmed but not operated on (Abnormal Failure alarms instead), and the feeder can't restore anyone else either. This is the one way "we never hit Reset" turns into "the DAC did nothing the second time." Operating order after a dirty event: fix the cause → Reset → confirm the feeder is no longer abnormal → RTN.
  • Live targets are flags, not a queue. A second permanent fault re-asserts the same event indicators, so the target list alone can't distinguish two events. The durable per-event record is the SOE log and the auto-generated post-event report — go there for event #1's story, not the targets.

2Abnormal conditions — what takes a feeder out of play

One abnormal device = the whole feeder abnormal = excluded from solutions (it still gets polled in Update). Bypassed and out-of-service devices are exempt from abnormal declaration. The device dispositions matter: Inhibit = don't operate, trust reported status; Bypass = don't operate, assume closed; Out of service = don't operate, assume open. Inhibited/bypassed devices can't sectionalize; out-of-service/inhibited devices can't restore.

Most “why didn't the DAC operate?” investigations end here: something on the feeder was abnormal, and one device is enough. (Animated in the browser.)

3Edge cases operators actually ask about

The questionWhat actually happens
A second fault hits while the first sequence is still executing.New events are detected in every step, and "new event" is an explicit exit from the Reconfiguration step — the system pulls back, re-evaluates, and solves all confirmed events together (sequential and concurrent faults are a listed core capability). The exceptions that abort outright mid-sequence: close-onto-fault and directional fault discrepancy.
Two feeders fault at once (storm).The reconfiguration sequence waits until every feeder's event sequence is idle, then evaluates all confirmed events in one solution pass — shared alternates get allocated by the criteria ladder, not first-come-first-served.
Dispatch manually opens a modeled breaker or switch. Will the DAC "restore" around it?No. A device operating without a fault indication is a manual operation — no DA event (stated explicitly for UFLS breaker trips). The area downstream of a modeled open device simply isn't part of any feeder (a feeder is a source feeding zones through closed devices), so no open-phase pattern exists on the energized side. The DAC keeps running AR on the new present topology.
Planned upstream / transmission switching kills station voltage.That is an event: loss of substation voltage is an open-phase (dead-bus) condition, and once the ~60 s confirm time runs out the DAC starts moving feeders to alternates. The 10 s detect delay only rides through brief switching transients. For planned upstream outages, disable the scheme or exclude the feeders first.
Will FLISR ever reclose the device that locked out?Only when it locked out upstream of the true fault — miscoordination correction, where the DAC isolates the real zone and then recloses the wrongly-operated upstream device. It never re-energizes the faulted zone itself.
A hot-line tag goes on mid-event.On the event feeder before confirmation: the sequence aborts to Idle with Abnormal Failure alarms. On a candidate alternate during Update/Analyze: that feeder is dropped from solution consideration. During execution: the sequence can abort on AbnormalCondition when the reconfiguration time limit expires.
The DAC reboots mid-event or while off-normal.Feeders come up in Initialize — internal variables and alarm conditions reset, the configuration re-evaluated, everything re-polled. The manual describes no mechanism for resuming a half-executed sequence, so expect the system as-switched, with targets rebuilt from live data, and finish by manual switching or RTN.
Operator disables the DAC to abort a sequence. Then what?The sequence stops — that's the designed abort. No rollback of already-executed switching is described: whatever opened or closed stays that way, and the cleanup is manual (or RTN once re-enabled and healthy).
An overload rides through a fault event.The fault wins. Overload monitoring only runs when no fault or open-phase condition is detected on the feeder and no abnormal conditions exist — the overload gets its turn afterward, when its (system-wide) confirm timer says so.
Can I RTN with the scheme disabled?No. RTN acceptance requires the feeder Armed — plus no events ongoing anywhere, no abnormals on the present or normal configuration, and RTN enabled in the system.
The deepest device never reports its fault indication.If it's comm-failed, the feeder is abnormal and the event is blocked — the protected case. If it's online but its FI logic just doesn't assert, the DAC locates the zone below the deepest FI it can see — one zone too far upstream, and isolation lands wrong. The manual's design assumption is FIs asserting on pickup at every device that saw fault current; this is why FI configuration is the make-or-break item.

Each answer above is built from explicit manual statements (event/RTN acceptance conditions, sequence exits, UFLS manual-operation rule, feeder definition, Initialize behavior); where a behavior is the absence of a described mechanism (reboot resumption, disable rollback), the entry says so rather than asserting a guarantee. For customer-facing procedures on those two, confirm with dac_support@selinc.com.

4Troubleshooting & fine print

  • "Why didn't it operate?" checklist: feeder Armed? abnormal tag anywhere on the feeder? did anything ever lock out (no lockout = no permanent fault)? open phase — was there an FI blocking it, or is voltage-discrepancy detection off? did Analyze or Update time out?
  • "Why did only part come back?" — CapacityLimit: margins, Level-1 voltage gates, nonpreferred-source penalties, or an abnormal neighbor. The event report has the scenario detail; the alarm doesn't.
  • After any event, expect the system off-normal until RTN — and remember RTN won't act at all if it can't do the whole job cleanly (§1).
