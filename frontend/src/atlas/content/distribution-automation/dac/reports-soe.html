DAC — Reports, SOE & Commissioning HMI

The four records the DAC produces, what each contains, and what simulation mode decouples

SOE shows, report explainspre-event every minuteDAC clock, not fieldsimulation mode

☰Core facts

  • The SOE shows what happened. The event report gives the reason. The SOE contains no explanation of AR operations, no loads lost or restored, and no reason for a failure.
  • SOE timestamps are the DAC's internal clock, taken when the data point updated inside the DA logic — not the field device's timestamp. Do not use the SOE for protection element analysis.
  • The pre-event report is the only record of what was already true before the event.
  • Simulation mode stops polling and stops all commands to the physical device. AR-generated controls toggle the simulated statuses.

1Event reports

Generated automatically for each reconfiguration, successful or unsuccessful. Contains which zones were affected, what load was lost and restored, and why a restoration was incomplete.

Content varies by adapter library version. Later versions added diagnostics for capacity-limited events, an indication of why devices were opened in open-phase events, reporting of relevant substation transformers, and better lost-load calculation for bus faults, switchgear faults and permanently looped systems.

2Sequence of events

The DA system logs all status changes from field or substation devices that impact AR functionality, plus all DA-generated statuses.

  • At least the most recent 30,000 events are stored, replaced oldest-first.
  • Downloadable as CSV from the RTAC web interface — log in, then SOE in the navigation menu.
  • The most recent 100 events display by default. Column headers sort; Filter options are above the table.

Logged: device communications statuses, open/close commands and statuses, fault and event indicators, abnormal status indicators, AR operational stages — anything eligible for SCADA reporting.

3Pre-event reports

Every minute the DAC writes a temporary log of all statuses of all devices. When an event trigger occurs, the last log written before the trigger becomes the pre-event report — a CSV of the system's condition immediately beforehand.

All statuses prior to the eventThe SOE records changes. A status steady for weeks does not appear in it. This exposes conditions such as a dead or blown PT reading dead voltage since before the event.
Loading conditions prior to the eventApproximate loading in the run-up. Shows which areas were tight where capacity restrictions shaped the outcome.

Pre-event report, SOE and event report together give what was true before, what happened, and why.

4Email reports

Four email types are available through the emailer function blocks. Three are commonly used.

EnableProduces
gv_EmailEventReportAn email after each successful or unsuccessful reconfiguration, with the event report attached.
gv_FeederState_BufferA notification after each reconfiguration summarizing the feeders involved and the cause. Not recommended if event report emails are enabled; the same information is in the report.
gv_Alarm_BufferA notification when one or more devices remain abnormal for a user-specified time, naming the devices blocking DA operation.

Server configuration and test-send hooks (SendTest) are in the emailer program. See the UDG's Email Configuration section.

5Commissioning HMI

A maintenance and commissioning tool, not for long-term or daily use. For a permanent HMI, license the RTAC for HMI and build graphics in AcSELerator Diagram Builder, or build the operator interface on the SCADA system from the DAC's reporting.

Requires no additional code, no additional statuses, and no RTAC HMI license. It is a visual display of the values already in each device's InputData and OutputData.

Simulation mode

Decouples a modeled device from communications with the physical device.

  1. The device stops polling the physical device and sends it no commands.
  2. All statuses latch at the value reported when simulation mode was entered.
  3. Statuses may be toggled from the HMI controls.
  4. Controls generated by AR operations toggle the simulated status as a manual toggle would, so the device displays the operations that would have occurred without operating real plant.
Fixed in adapter V2.9.4: devices left in commissioning mode could cause load duplication and produce solutions with false overloads.

6Library version

The OM carries a revision log per adapter library version. Behavior changes:

  • V2.10.4 — fixes for non-gang reclosers with one or two poles open potentially closing into energized circuits, blocking RTN, or letting RTN switch beyond its allowed boundaries. Improved SOE logging of feeders adjacent to devices.
  • V2.10.3 — fixes IsolateBreakerZone failing to isolate the breaker zone for certain upstream events.
  • V2.10.1 — Feeder Overload Warning reports even when overload mitigation is disabled.
  • V2.10.0 — where initial conditions would have the DAC both open and close the same device (opening for breaker-zone isolation while closing for miscoordination correction), the DAC now prefers opening. Improved fault-latch reset for back-to-back events.
  • V2.9.2 — fixes fault pickup latching indefinitely when a device detects a fault then becomes electrically isolated by a non-event condition such as manual switching.
Both controllers in a distributed pair must run exactly the same DA and Adapter library versions. See System-Level Optional Features.
