Picking a protocol

  • Speed decides first. Under about 100 ms it is GOOSE, Mirrored Bits, or a wire. Above that, everything else is available.
  • The master usually decides northbound. What the control centre speaks is a given; your job is to translate to it, not to argue with it.
  • Timestamps at the source are worth a great deal. DNP3 and IEC 61850 carry event time; Modbus does not, so the RTAC has to invent one at scan time.
  • Modbus is universal and minimal. Registers and coils, no data model, no events, no quality, no time. Every device speaks it, and that is its whole argument.
  • IEC 61850 buys self-description and speed; it costs tooling, engineering discipline, and a managed network.
  • The RTAC is the translator. A device that speaks only one protocol is fine if the RTAC can speak it — see RTAC Tags.

2The dimensions that actually decide it

DimensionWhy it matters
LatencyThe hard constraint. Polled protocols cannot make protection-speed decisions no matter how fast the network is

Data modelSelf-describing (IEC 61850), semi-structured with object types (DNP3), or raw registers you must map by hand (Modbus)
QualityCan the protocol say “this value is stale / invalid / substituted”? A value with no quality is a value you must trust blindly

DiscoveryCan the tool read the device's capabilities, or do you type a map from a PDF?

The Modbus tax is real and it is paid at commissioning. No events means the RTAC polls and compares, so timestamps come from the scan rather than the device, and fast transitions between polls are simply lost. No quality means a device that has stopped answering may look identical to one reporting zeros, unless you build the offline logic yourself. None of this makes Modbus a bad choice — it makes it a choice with known homework. See Modbus on the RTAC.

4Southbound and northbound

The RTAC sits between two worlds and the two directions have different constraints. Keeping them mentally separate prevents most architecture arguments.

Southbound (RTAC → field devices)Northbound (RTAC → SCADA master)
Who choosesYou do, within what the device supportsThe master's owner, usually before you arrive
Typical choiceSEL protocol to SEL relays; DNP3 or Modbus to third-party devices; GOOSE for fast bitsDNP3, or IEC 61850 / 60870 where mandated
Optimize forRich data, source timestamps, easy configurationA stable, documented point list that will not churn
Change frequencyChanges when devices changeChanges require coordination with the control centre — treat the northbound map as a published interface
Failure visibilityDevice offline status becomes a tagThe master must be able to tell “RTAC lost the relay” from “the value is really zero”
Do not let the northbound map dictate the southbound design. If the master only wants twenty points, you should still bring in everything useful from the relay and expose twenty. Data you did not collect cannot be added retroactively to a historian, and the marginal cost of collecting it southbound is close to zero.

5Intake questions for any third-party device

  1. Which protocols, and over which physical layers? “Modbus” alone is ambiguous — RTU or TCP, and on which port?
  2. Is there a published register or point map, and does it match the firmware actually shipped?
  3. What is the addressing convention? Zero-based or one-based registers is the single most common integration error — see Modbus Fundamentals.
  4. Data types and word order. 32-bit values split across two registers can be big- or little-endian, and vendors disagree.
  5. Scaling. Is the value already engineering units, or does it need a multiplier the manual mentions in a footnote?
  6. How many simultaneous sessions does it support? Some devices allow exactly one, which means SCADA and your laptop cannot both be connected.
  7. What does it do when it loses the master? Hold last value, go to zero, or fail safe?
  8. Controls: supported? Select-before-operate? Does it confirm the outcome, or just accept the command?
  9. Time: can it be synchronized, and does it timestamp anything?
  10. Security: can credentials be changed, and are the defaults documented publicly?

Answer these before the device arrives, not during the outage window. The RTAC-side workflow for a device like this is in Modbus on the RTAC.

6Gotchas

  • Choosing by familiarity rather than by requirement. Modbus because you know it, on a device that speaks DNP3, throws away timestamps and events for nothing.
  • Assuming one protocol per device. Most modern IEDs speak several simultaneously — a relay can serve DNP3 to the RTAC, GOOSE to its neighbours, and SEL ASCII to your laptop at once.
  • Running a protection function over a SCADA protocol because it worked on the bench. It will work most of the time, which is the worst possible failure mode.
  • Two masters, one outstation, no plan. Multiple sessions to one device need address, session, and event-buffer planning — each DNP3 server keeps its own event queue.
  • Point maps that drift. The map in the relay, the map in the RTAC, the map in the master, and the map in the spreadsheet must be one thing. See SCADA Integration.
  • Ignoring quality. A protocol that carries quality is only useful if the receiving side acts on it. Map it through and use it.
  • Forgetting the engineering-access path when planning ports and sessions. It is a real requirement, not an afterthought.
