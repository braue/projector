☰The rules, stated plainly

DNP3 in general

  • DNP3 is event-oriented: the outstation remembers what changed; the master mostly collects events instead of re-reading everything.
  • Every piece of data is an object group + variation at a point index. The variation is just the format of the same value.
  • Class 0 is present values. Classes 1/2/3 are buffered change events. Assigning a point's event class is what makes it report by exception.
  • Quality flags travel with the data. A value without its flags is half a value.
  • Every response carries IIN bits — the outstation telling you it has events, needs time, restarted, or overflowed. Read them.

1The shape of the protocol

DNP3 (IEEE 1815) is a SCADA protocol between a master and an outstation, built as three layers that survive noisy channels:

Link layerFT3 frames, 16-bit source + destination addresses, CRC every 16 bytes
→
Transport functionsplits large application messages across frames and reassembles them
→
Application layerfunction code + object headers + data; fragments confirmed and sequenced

It runs over serial (including multidrop — several outstation addresses on one line) or IP, where the same frames ride TCP or UDP, conventionally port 20000. Device addresses run 0–65519; 65535 is the all-stations broadcast. One physical device can host several DNP sessions, each with its own address pair and its own event queues.

2The data model: objects, variations, classes

Everything the outstation exposes is a numbered point inside an object group. The group says what kind of data; the variation says the encoding (bit width, flags, timestamp). Masters can request variation 0 — "give me your default."

Classes are the routing layer for events. Class 0 means "current value of everything." Each event-capable point is assigned to Class 1, 2, or 3 (or None); a change beyond its deadband generates a buffered, timestamped event in that class. A point assigned Class None generates no events — and on the RTAC, Event Class None also excludes it from Class 0 responses.

Quality flags ride with most variations: online, restart, comm-lost, remote/local forced, chatter (binaries), over-range and rollover (analogs/counters). Comm-lost propagating through an RTAC to SCADA is how the master learns a downstream IED went dark without the point ever changing value.

3How data actually moves

1 · Integrity pollClass 1,2,3,0 — all buffered events, then a full snapshot. At startup and on restart/overflow.
→
2 · Event pollsClass 1/2/3 on a short period — only what changed. The steady-state workload.
→
3 · Unsolicitedoutstation pushes events on its own when thresholds are met (if enabled).

That order matters: events first, snapshot second, so the master never overwrites fresh events with an older static value. Report-by-exception is what makes DNP3 cheap on bandwidth — a quiet substation produces near-zero traffic between integrity polls.

The three ways data moves, in the order a healthy session uses them. ▶ Animated in the HTML edition.

  • Deadbands create analog events. A point generates an event when it moves beyond its deadband from the last reported value. Deadband of 0 = an event on every scan — this burdens the device and the channel; don't do it.
  • Event buffers are finite. SEL-751A: 1024 binary / 100 analog / 32 counter events per session. On overflow the outstation raises IIN2.3 and the master should integrity-poll to resynchronize.
  • Unsolicited needs discipline on multidrop serial: two outstations pushing at once collide. The RTAC server offers randomized transmit min/max delays for exactly this; relays gate unsolicited with count (NUMEVE) and age (AGEEVE) thresholds, plus retry and offline timers.

Report by exception: an analog generates an event only when it moves beyond the deadband from its last reported value — then the band re-centers there. ▶ Animated in the HTML edition.

4IIN bits: the outstation's status line

Every response carries two Internal Indication bytes. These are the protocol's health telemetry — masters that ignore them miss restarts and lost events.

BitMeaning
IIN1.0Broadcast message received
IIN1.1–1.3Class 1 / 2 / 3 events available — "come poll me"
IIN1.4Need time — clock wants a sync
IIN1.5Local control — some points switched to local
IIN1.6Device trouble
IIN1.7Device restart — expect an integrity poll
BitMeaning
IIN2.0Function code not supported
IIN2.1Requested objects unknown
IIN2.2Parameter error in request
IIN2.3Event buffer overflow — events were lost
IIN2.4Operation already executing
IIN2.5Configuration corrupt

The RTAC client auto-responds to IIN1.1–1.3 (polls the flagged class) by default — visible as the Auto_Respond_to_IIN_* POU pins. Auto-respond to Need Time is default FALSE: the RTAC won't time-sync an IED unless you enable it. The RTAC server exposes force pins for IIN1.6 and IIN2.3 so logic can flag trouble upstream.

5Time: sync and timestamps

Two separate problems live here — setting the outstation's clock, and trusting the timestamps on events.

  • Syncing: the master writes time (Object 50; Var 1 with Object 52 delay compensation on serial, Var 3 for LAN/WAN). SEL relays treat DNP time as backup only — the manuals state its accuracy is insufficient for protection and oscillography; IRIG-B is the real source. The per-session TIMERQ setting picks the posture: I (default — accept the write, ignore it), M (accept and use), or a period (actively request sync via IIN1.4).
  • Timestamps: on SEL relays, ordinary binary inputs are scanned for DNP events at ~1–2 scans per second, and the event carries scan time — up to a second late. Points registered in the SER carry the true time of occurrence. Never build sequence-of-events analysis on non-SER DNP timestamps.

6Troubleshooting & fine print

  • IIN1.7 (restart) or IIN2.3 (overflow) seen? Integrity-poll before trusting anything — buffered history is suspect.
