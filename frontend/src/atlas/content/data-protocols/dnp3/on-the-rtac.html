☰The rules, stated plainly

Controls

  • Verb tags fire on the rising edge of ctlVal. One scan of TRUE = one control sent.
  • Holding ctlVal TRUE does nothing extra. It only blocks the next control until it goes FALSE.
  • A failed control never retries itself. Re-issue with a fresh edge.
  • The per-point On/Off Pulse Duration and Number of Pulses settings fill the CROB's timing fields.
  • RTAC and Axion contact outputs do execute those durations, rounded up to the task cycle.

Data & polling

  • The client integrity-polls at startup, then runs class polls. Controls jump the queue — an outstanding poll is interrupted.
  • The server keeps a separate event queue per server device, even when several share one map.
  • Nothing flows by itself: the Tag Processor moves data between client tags and server maps.
  • Server event buffers default to one entry per tag — latest value only. Configure SOE mode for true event history.

1Controls: six tags, one pulseConfig

Both the RTAC's DNP client and server maps create every binary output as one base point (BO_00007) with six members: .status (SPS) plus one operate structure per verb. All five verbs exist on every point — the RTAC does not pick a control model for you; it will build (or accept) any of the five codes. Model discipline lives in your logic and your published points list.

Edge-triggered: a control fires only on the FALSE→TRUE transition. The long hold sends nothing extra; the second control needs a fresh edge. ▶ Animated in the HTML edition.

Does it matter how long you hold ctlVal high? No. One scan of TRUE issues exactly one control; ten more seconds of TRUE issues nothing more. The hold time only affects re-arming — the value must go low before the next control can fire. The idiom is a one-scan assert. Continuous assignment (ctlVal := SomeCondition;) is safe but fires only on the FALSE→TRUE transition of the condition. And a failed control never retries itself — check the outcome and re-issue with a fresh edge.

The timing settings

On the device's Binary Outputs settings tab, each verb row has four columns — Control Model (Pulse | Persist), Number of Pulses (default 1), On Pulse Duration (default 2000 ms), Off Pulse Duration (default 2000 ms). They initialize the verb's pulseConfig; logic can overwrite it at run time before asserting ctlVal. The latch verbs carry the columns too, but latch codes have no timing.

As client, as server, as contact

  • Client: a rising edge on a verb's ctlVal makes the client build the CROB from that verb's code + pulseConfig and send it (SBO or direct per Output Control Type; a pending poll is interrupted for it). .status is filled by static polls of Object 10 — the state the outstation reports, not proof the process moved.
  • Server: an incoming CROB routes by control code to the matching verb tag (0x81 → operTrip.ctlVal, 0x01 → operPulse.ctlVal, …). Your logic or Tag Processor acts on the verb and writes feedback into .status — nothing updates automatically. Configure the executed pulse timing on the RTAC point; don't rely on the master's CROB on-time passing through. The Tag Processor can also convert verb types end-to-end (SCADA trip/close → IED latch on/off) by matching the Control Type column.
  • Contact outputs: RTAC and Axion digital outputs run pulse trains natively — assert onDur, deassert offDur, repeat numPls times, quantized up to RTE-cycle multiples (100 ms task: onDur 97 → 100 ms, offDur 103 → 200 ms). operClear cancels a pulse in progress; numPls=0 or onDur=0 also cancel; offDur=0 merges into one continuous onDur×numPls assertion. The PulseDecoder function block gives the same behavior to any BOOL in logic.

2Data: client polling and server maps

As client (master)

  • Issues an integrity poll at communications startup, then periodic integrity and class polls (typical settings: integrity every 60 s, Class 1/2/3 every few seconds, with poll timeout and retry counts per session). Controls interrupt an outstanding poll.
  • Beyond the built-in polls, up to 15 custom requests per session cover anything else: explicit object reads, counter freezes, etc.
  • Client and Server DNP Address settings mirror the relay's REPADR / DNPADR — the most common "no comms" mistake is crossing them.

As server (outstation)

Shared map defines what the points are; each server device owns when its master last saw them. (Animated in the browser.)

  • Server points live in a DNP Server Shared Map (up to 100 maps, 10,000 tags per type) that the Tag Processor populates. Several server devices can share one map — but each keeps its own event queue, so two masters each get their own copy of every event.
  • Event buffers are per type (binary/analog/counter), sizable 1–65,535. Default is one entry per tag — latest change only. SOE mode buffers everything; on overflow the oldest events are kept and new ones discarded, so poll fast enough.
  • Each point carries a per-point Event Class (binaries default Class 1, analogs Class 2, everything else Class 0 / static-only).
  • Ethernet servers either allow anonymous clients or enforce an allowlist of up to 20 client IPs; serial servers can share one port as a virtual multidrop, and failover to a second serial or tunneled path with one shared event queue. Secure Authentication v5 is available (R143+), with per-function-code challenges and DNP user roles.
  • Capacity: 200 DNP clients/servers on most models, 500 on the SEL-3560 class.

3Troubleshooting & fine print

  • No comms, addresses look right? Check both directions: relay DNPADR = RTAC's Server DNP Address and relay REPADR = RTAC's Client DNP Address. On Ethernet also the relay's configured master IP (DNPIP) and the RTAC server's client-IP allowlist — both ends filter by address.
  • Don't map the same server index twice on an RTAC shared map — duplicate indices don't generate events.
  • After a failover or second master connects, remember each RTAC server device has its own event queue: master B gets its own event history, not what master A already read.
  • Any verb is live on every RTAC point. operPulse to a trip/close point isn't blocked by the RTAC — the outstation's model decides. Asserting two verbs in the same scan is two separate controls, not a merged one.
