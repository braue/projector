Synchrophasors

GPS-referenced phasors and IEEE C37.118 — PMUs in relays, PDC time alignment, and doing real-time work with wide-area angles

C37.118PMUPDCMRATEIDCODETSOKTVE ≤1%UDP_S/T/U

☰The rules, stated plainly

  • A synchrophasor is a phasor whose angle is measured against absolute time (a GPS-disciplined clock, delivered as IRIG-B). Because every PMU uses the same time reference, angles from any two substations are directly comparable.
  • No high-accuracy time, no synchrophasors. On the SEL-451 the data are only valid in HIRIG timekeeping mode (TSOK = 1). Clock loss doesn't stop the stream — it degrades the time-quality flags riding in every frame.
  • Everything is identified by station name + IDCODE, and they must match exactly at every hop (case and trailing spaces included).
  • The PDC's per-output Waiting Period is the latency-vs-completeness knob: data arriving later than it are zero-filled and flagged, not waited for.
  • Rates: a relay streams 1–60 messages/s (MRATE); a PDC output rate must be a common divisor of its input rates.

1What a synchrophasor is

"Synchrophasor" = synchronized phasor: measurements taken on a synchronized schedule in multiple locations, made possible by a high-accuracy clock — commonly a GPS receiver such as an SEL-2407 (SEL-451 IM). The PMU samples on a constant-time basis locked to IRIG-B, at 50 or 60 sets per second (NFREQ), and measures each phase angle relative to an absolute time reference represented by a cosine wave that peaks at the top of each second. Magnitudes are rms, scaled to primary units by the PT/CT ratios. Each data set carries its time-of-sample (second-of-day and fraction-of-second).

That absolute reference is the entire point: a conventional relay measures angles relative to its own sampling clock, so angles from two devices mean nothing to each other. Two PMUs referenced to the same GPS second produce angles you can subtract — and the difference between bus voltage angles across a transmission path is a direct, live image of power transfer. One honest wrinkle (SEL-451 IM): the power system rarely runs at exactly nominal frequency, so successive synchrophasors of the same signal almost always show some angular change — the phasor slowly rotates against the fixed time base. That is normal, not a malfunction.

2Why not just SCADA? (AN2006-10)

SEL AN2006-10 makes the case in the context of state estimation. A SCADA system gathers breaker status, P/Q flows, and voltage magnitudes from meters and IEDs within a polling window that is typically a few seconds long — and to be fair, when the system is in steady state that time skew introduces no error at all. The traditional estimator then computes bus angles from P/Q measurements plus branch parameters relative to one angle reference.

Failure modeSCADA-based estimationSynchrophasor measurement
System state changing fastMeasurements inside the multi-second window are inconsistent with each other; undetected topology changes mid-poll can make the estimate failEvery value in a data set shares one timestamp; breaker status is reported with timestamps synchronized to the measurements
Missing critical dataLose the branch measurements linking two regions and one region's angles become unrecoverable relative to the referenceAngles are referenced to a global reference — one PMU per region is enough to tie both regions to the same reference; fewer measurements are critical
Bad network parametersComputed angles inherit errors from branch impedance data, which "are not always accurate"Angles are measured directly; no dependence on network parameters

The honest summary: SCADA answers "what are the magnitudes and flows, roughly now." Synchrophasors answer "what was the exact voltage phasor at every instrumented bus at 10:00:00.000" — 30 times a second in a typical build (AG2009-15 uses MRATE := 30), with angles that are directly comparable grid-wide.

3C37.118 on the wire

IEEE C37.118, Standard for Synchrophasors for Power Systems (the SEL fleet documented here implements C37.118-2005), defines four frame types. Data flows only after the client commands it: a PMU will not transmit until it receives the start/enable command, stops on the stop command, and answers configuration requests only while not transmitting (SEL-451 IM).

Data frameThe repeating payload: STAT word, phasors, frequency + df/dt, analogs, digital words. Time in SOC + FRACSEC, with time-quality bits inside FRACSEC.
CFG-1 / CFG-2Machine-readable capability (CFG-1) and current configuration (CFG-2) frames — the client requests these to auto-build its database. Max config frame 65 536 bytes.
Header frameHuman-readable descriptive text (e.g. the SVP's HEADER_118 string, up to 256 characters).
Command frameClient → server: start request, stop request, configuration request 1/2 (per the SEL-3373's protocol diagrams).

Message rates and size

The rate is fixed by the sender's settings — with C37.118 the client cannot negotiate it in the enable message (unlike SEL Fast Message synchrophasors). SEL-451 MRATE choices: 1, 2, 4, 5, 10, 12, 15, 20, 30, 60/s on a 60 Hz system; 1, 2, 5, 10, 25, 50 on 50 Hz. The SEL-3373 PDC handles up to 240/s (60 Hz) or 200/s (50 Hz). An SEL-451 data frame is 18 fixed bytes plus 4 or 8 bytes per phasor (integer vs. float), 4–8 bytes of frequency + df/dt, 4 per analog, 2 per digital word — 22 bytes minimum, 158 max. That matters on serial: the smallest practical message (one phasor + one digital word, 26–34 bytes) runs at any MRATE only at 38400/57600 bps; a fat float message may cap out at MRATE := 12 at 19200 bps. The relay refuses to save settings the port SPEED can't carry.

Loss tolerance is the design choice: TCP retransmits, UDP variants accept loss for latency — fine for visualization, wrong for an archive. Serial C37.118 also exists (SEL-451 ports 1/2/3/F with PROTO := PMU; SEL-3373 has 16 serial inputs).

4PMU in the relay — the SEL-451

Enable with Global EPMU := Y (nothing else appears until you do), pick the protocol with MFRMT := C37.118 (the legacy alternative is FM, SEL Fast Message — one protocol per installation, though it can run on several ports at once). Then the settings fall into four groups:

Rate & filteringMRATE, PMAPP, PHCOMPMessages/s; filter class — PMAPP := N (narrow band, alias-free, for post-disturbance analysis; accuracy spec applies here) vs F (fast response, for speed in tracking); frequency-based compensation for off-nominal accuracy (Y unless concentrating with PMUs that don't compensate)

  • Serial: set the port's PROTO := PMU (fixed 8-N; that port then answers no ASCII commands — if you set your engineering port to PMU, recover via another port or the front panel). FASTOP per port gates whether Fast Operate controls are accepted over the synchrophasor channel.
  • Ethernet: EPMIP := Y plus two independent PMU outputs, each with transport PMOTSx (OFF/TCP/UDP_S/UDP_T/UDP_U), client IP, and ports (defaults 4712 TCP / 4713 UDP data).
  • Triggers: SELOGIC equations PMTRIG + TREA1–4 ride in every data frame's STAT field; C37.118 defines codes 0x00–0x07 (manual, magnitude low/high, phase-angle difference, frequency, df/dt, digital), 0x08–0x0F are user-defined. The relay never sets these itself — you program them, and hold PMTRIG asserted long enough for the processor to read the reason bits.
The time-quality requirement. Synchrophasors are valid only when the relay is in high-accuracy timekeeping (HIRIG) mode on IRIG-B — watch Relay Word bits TSOK (time sync OK, sufficient accuracy for synchrophasors) and PMDOK; even MET PM refuses to run without TSOK. When MFRMT := C37.118, the IRIGC setting is forced to C37.118 control-bit decoding. Rated accuracy: TVE ≤ 1% across ±5 Hz, 30–150 V, 0.1–2×Inom, ≤10% harmonics. Clock distribution, IRIG-B wiring, and time-quality itself are covered in Time Synchronization in atlas.

5The PDC — SEL-3373 Station Phasor Data Concentrator

A PDC turns many per-PMU streams into one time-aligned stream. The SEL-3373 takes 8 (optionally 40) PMU inputs over serial or Ethernet, aligns frames by the timestamps inside the data (never by arrival time), and each output "combines a set of time-aligned PMU data into a concentrated data packet" — a superpacket per timestamp, sent on up to six independently configured Ethernet outputs. Average latency through the box: <10–30 ms depending on load.

The alignment pipeline: frames from three PMUs arrive skewed and are slotted by timestamp, not arrival order. When the waiting period expires, the row ships regardless — PMU C's late data is zero-filled, its STAT flags set, and the late frame discarded on arrival. ▶ Animated in the HTML edition.

  • Waiting Period — set per output (spec range 0–120 s; a Global Maximum Waiting Period caps them all and bounds how long calculations wait). Longer window = more complete data, more latency. The Real-Time status page reports per-input network latency max/avg and a max−min "Differences" row expressly so you can set the waiting period from measured skew. Data arriving past the window: tags zero-filled and counted missing.
  • Bad clocks get voted out. A majority vote across input timestamps discards frames stamped in the past or future beyond the waiting period (a PMU with a wrong clock); the victim's slots are zero-filled with STAT bits 15, 14, 13, 5, 4 set. Out-of-order packets inside the window are re-sorted — timestamps, not arrival, define order.
  • Rates must nest. An output's Data Rate must be a common divisor of its inputs' rates (60 + 20 msg/s in → out at 20, 10, 5, 2, or 1). Output phasors are IEEE 754 floats, polar or rectangular per output.
  • Forwarding & cascading: an output is a set of tags cherry-picked across PMUs and PDC calculations; export it as a .pdcx file and import it as a PDC input on the downstream (control-center) PDC — sub-PMUs and tags auto-populate (IP addresses are stripped from the export deliberately). Redundant inputs (primary/backup PMU streams, fail-over 1 ms–1 s, best stream chosen by the C37.118 quality bits) and redundant/multicast outputs are built in.
  • Archives: continuous or triggered (pre/post-trigger up to 90 min, trigger = any PMU trigger bit), each with its own waiting period; retrieval in COMTRADE or CSV. Onboard calculations (sequence components, phasor math, dx/dt, PMU latency) become tags like any other.

6Doing something with the phasors — SEL-3378 SVP

The Synchrophasor Vector Processor is where streams become decisions. Its Time Alignment Client Server (TCS) time-correlates C37.118 frames from up to 20 PMCUs (serial or Ethernet) into a single aligned frame — a PDC in its own right, serving one internal client plus six external C37.118 clients — and hands the aligned data to IEC 61131-3 user logic running on the real-time system. Documented function blocks:

BlockWhat it does
PADMPhase Angle Difference Monitor — angle difference between two chosen phasor angles (±180°), two thresholds in degrees with pickup timers, timestamped alarms. The manual's SIPS example trips excess generation when the bus-angle difference between areas crosses a threshold
MAModal Analysis — up to 6 instances; feed it frequency, magnitude, angle, power, or an angle difference; per mode it returns frequency, damping constant, damping ratio, amplitude, and phase — real-time oscillation detection driving alarms and remedial action
PWRCReal/reactive power (kW/kVAR) from selected V and I phasors, timestamped
SSTPSubstation State and Topology Processor — flags measurement errors, computes unbalance and symmetrical components, refines V/I measurements
FOFast Operate commands back out over the same C37.118 channels — set/clear/pulse remote bits, open/close breakers on the source relays
Local PMCUA user-configurable C37.118 server publishing your computed results (e.g. MA modes) to one external client such as SYNCHROWAVE Console

The loop that makes it a control platform, not a historian: measure everywhere → align → compute (angle difference, modes, power) → act via Fast Operate — all within the real-time stream.

8Field gotchas

  • Clock loss doesn't stop data — it poisons it quietly. The stream keeps flowing with degraded time-quality bits (FRACSEC) and STAT sync flags; the PDC's backup-input selection and status pages key off exactly those bits. On the relay, watch TSOK; on the PDC, the per-input Time Quality and Unlock Time columns.
  • "Waiting for Silence" on a PDC input = station name / PMU ID mismatch — case matters, embedded spaces matter, trailing spaces are not supported. Toggling "Configuring ↔ Not Connected" = ID or transport-scheme mismatch; check the UDP data/command port pairing.
  • Rate mismatches: the PMU's message rate must equal the PDC input's configured receive rate; output and archive rates must divide the input rates (mixed-rate PMUs can't share a triggered archive at all).
  • Output shows Missing Data: either tag names don't match what the PMU actually sends (use Query Tags), or data is arriving later than the output waiting period — zero-filled and counted missing. Measure the latency Differences row, then set the window.
  • Budget the bandwidth per stream: serial chokes fast (see the §3 size math — the relay enforces it at settings save); on Ethernet the 65 536-byte CFG frame limit caps tags per PDC output. More phasors × higher MRATE × float encoding all multiply.
  • A PMU serial port goes deaf on purpose: PROTO := PMU disables ASCII/engineering access on that port — plan which port you'll use to get back in.
  • No data at all from a PMU? C37.118 transmission starts only on the client's start command — a PMU that was never commanded (or whose client can't reach the command port) sits silent by design.
