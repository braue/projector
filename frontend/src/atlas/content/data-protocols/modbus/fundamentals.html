☰The rules, stated plainly

Modbus in general

  • Modbus is pure polling: the client (master) asks, the server (slave) answers, and the server never speaks unprompted. No events, no timestamps, no quality flags — you get exactly what you poll, when you poll it.
  • Everything is a 16-bit register or a 1-bit coil. What a register means — sign, scaling, word order — lives in the device's map documentation, not in the protocol.
  • 4X/3X addresses are documentation conventions. On the wire everything is 0-based: "40001" is holding register 0. Getting this wrong shifts every value by exactly one register.
  • The function code — not the address — decides which of the four data spaces you're reading.
  • A frame that fails its CRC is silently discarded. "No response" is Modbus's only error signal for a corrupted or misaddressed frame; the client just times out.

1Where Modbus fits

Modbus is the industrial world's lowest-common-denominator protocol — the common tongue of PLCs, HMIs, DCSs, meters, and protective relays in automated industrial plants. It predates SCADA protocols like DNP3 by design philosophy as much as by age: it standardizes only how to move register values, and leaves everything else (meaning, scaling, events, time) to the devices at each end. The protocol spec itself is maintained by the Modbus user's group at modbus.org; every SEL manual points there for the full text. Two wire forms matter in practice: Modbus RTU (binary, over serial) and Modbus TCP (the same function codes and data maps carried over Ethernet, registered port 502). The RTAC also speaks RTU tunneled inside TCP; Modbus ASCII is legacy and unsupported on the RTAC.

The consequence: on Modbus, bandwidth scales with the size of the map, not the rate of change — a quiet plant costs as much to poll as a busy one. Anything event-driven (SOE, alarms with time) needs DNP3, or a device like the RTAC time-tagging Modbus data as it arrives. See DNP3 Fundamentals in atlas for the other side of this table.

2Roles and topology

Modbus RTU permits communication between a single master (client) and multiple slave (server) devices, half duplex — only one device transmits at a time. The master transmits a query carrying the address of the slave it wants; every slave on the line receives the message, but only the one with the matching address responds. Addresses run 1–247 (SEL relays and the 735 meter set theirs with the SLAVEID port setting; the RTAC client's is Server Modbus Address); on traditional serial lines 248–255 are reserved. No two slaves on a network may share an address.

  • Broadcast — address 0. An RTAC Modbus client assigned address 0 becomes a broadcast client: it issues write commands (coil / holding-register function codes) that every server on the multidrop network processes regardless of address. Servers do not respond to a broadcast, so there are no retries (Poll Timeout and Poll Retries are ignored) and the client's Intermessage Transmit Delay must space requests so the writes don't pile up on the shared line. No polls — broadcast is write-only.
  • Multidrop serial: the classic deployment is several servers on one EIA-485 pair, one master polling them round-robin by address. The idle gap between messages is what separates one RTU frame from the next — RTU has no start/stop delimiter bytes, which is why spacing settings like the RTAC's Intermessage Transmit Delay exist at all.
  • TCP: each client opens its own TCP connection to the server's IP and port. On Modbus TCP the IP address is the primary identifier (the SEL-751 and 751A both use the device IP as the Modbus identifier); the unit-ID byte in the header still follows RTU addressing rules and matters when a gateway sits in the path.
  • Gateways / port servers: a port server doing Modbus TCP → Modbus RTU translation fronts a multidrop RS-485 chain with a single IP — the client picks the target device with the unit ID, and the gateway forwards the query onto the serial line. The RTAC can emulate exactly this (several TCP servers with unique addresses 1–247 sharing one port), and its address 255 is reserved to mean "answer any unit ID in the query."
  • Session limits are per-device: the SEL-751 and 751A each support up to two concurrent Modbus TCP sessions; the SEL-735 supports five; an RTAC Modbus server instance accepts exactly one client connection at a time ("connect and stay connected").

Companions: relay-side port settings, user maps, and coil semantics → Modbus on SEL Relays; RTAC client/server configuration, polls, tags, and shared maps → Modbus on the RTAC.

3Modbus RTU: the frame and the transaction

The master initiates every exchange by sending a query built from four fields. There is no length field and no frame delimiter — the function code implies the layout, the CRC closes the frame, and line silence separates one frame from the next.

RTU frame fieldSizeNotes
Slave device address1 byte1–247 — which server should answer; 0 = broadcast (writes only); 248–255 reserved on serial
Function code1 bytewhat to do — which data space, read or write (§6)
Data region0–251 bytesaddresses, counts, and values; each byte 0–255
CRC-162 bytescomputed over address + function code + data, appended at the end of every message

CRC behavior, exactly as the 751/751A manuals describe it (identical text in both): the relay calculates the 2-byte CRC from the device address, function code, and data region and appends it to every response. The master recomputes the CRC on receipt; if it matches, the data is used — if not, the message is ignored. The same process runs in the other direction for queries: a slave that detects a CRC error discards the packet. Nothing is sent back. A response is only ever formatted like the query — same slave address, same function code, data, CRC — or, if the query can't be executed, an exception response (§8) with the function code's most significant bit set.

One RTU transaction, then the failure branch: fields assemble in order, the CRC seals the frame, and a frame corrupted in flight is discarded without any reply — the master's timeout is the only notification. ▶ Animated in the HTML edition.

4Modbus TCP: the MBAP header

Modbus TCP wraps the same function-code + data payload in a 7-byte header (the MBAP header) instead of the RTU address + CRC. The SEL-735 manual documents the message format byte-for-byte:

BytesFieldServer action / notes (per SEL-735 Table E.22)
0–1Transaction identifiercopied into the response — lets a client match replies to requests on one connection
2–3Protocol identifiercopied into the response; zero for Modbus
4–5Lengthlength of the data that follows, in bytes (upper byte zero while messages are under 256 bytes)
6Unit identifierfollows Modbus RTU addressing rules — this is where a gateway reads the target slave address
7Function codecopied into the response if no error; high bit set on an error condition
8…Datathe request data, response data, or exception code
  • No CRC field. The TCP message format ends at the data region — frame integrity is the transport's job, not the protocol's. The silent-discard behavior of §3 is an RTU phenomenon; on TCP a broken connection is what "no answer" looks like.
  • Port 502 is the registered Modbus TCP port (SEL-751, 751A, and SEL-735 all default to it; the 751 and 751A let you move each session's port with MODNUMn).
  • Multiple sessions: each client is a separate TCP connection. Device limits differ (§2) — 751A two sessions, 735 five, RTAC server one per server instance — so "the SCADA guy connected and now my test client can't" is expected behavior, not a fault.
  • Same maps, same codes: the 751 and 751A manuals state it directly — Modbus TCP accesses the data in the relay using the same function codes and data maps as Modbus RTU. Everything in §5–§8 applies to both transports. (The SEL-751 adds one TCP-only guard: MODIP1/2 can pin each session to a configured master IP.)

Same PDU, two transports: on TCP the MBAP header (with its echoed transaction ID) replaces address + CRC and each client has a private connection; on RTU one shared pair carries every frame to every device and the address byte decides who answers. ▶ Animated in the HTML edition.

5The register model and the off-by-one trap

A Modbus server exposes four data spaces. Each is addressed from 0 within its own space; which space you land in is decided by the function code, not the address.

SpaceLegacy prefixWidthAccessFunction codes
Coils (discrete outputs)0x1 bitread/write01, 05, 0F
Discrete inputs1x1 bitread-only02
Input registers3x16 bitread-only04
Holding registers4x16 bitread/write03, 06, 10
The off-by-one trap. Addresses like 30001/40001 are a legacy documentation convention that folds the register type into the number — the RTAC manual states they "are for documentation purposes only and are not actually used in the Modbus protocol." On the wire, addressing is 0-based. The SEL-751 and 751A manuals give the translation both ways: masters accustomed to 4X references with FC 03 should "add 40001 to the standard database address" for five-digit addressing (add 30001 for 3X/FC 04); for the write codes 06h/10h with six-digit addressing, add 400001. The RTAC is 0-based everywhere — a third-party device's "40001" is configured as holding register 0 in the RTAC project, and Coil 1 on the 751/751A lives at coil address 0. When every value sits exactly one register away from where you expect it, this is why.

Note that a device is free to point two spaces at the same data: on SEL-700 series relays, FC 03 and FC 04 read the same register map (the 751A points both at its Table E.34, the 751 at its Table E.35), while FC 01 reads the coil/control list and FC 02 reads Relay Word bit status — two genuinely different bit spaces.

Writes have device-specific semantics behind the generic verb — on the 751A, "writing a coil" pulses an output for 1 second or sets/clears/pulses a remote bit depending on the coil address. That, plus user maps and settings-write protection (BLKMBSET), lives in Modbus on SEL Relays.

7Data encoding: 16 bits and everything built from them

Registers are 16 bits, full stop. Every richer type is a convention layered on top — and the server's manual, not the protocol, is what tells you which convention a given address uses. The client's configuration must match what the server sends, or the numbers will be plausible and wrong.

Register typeRangeRegister typeRange
16-bit signed−32 768 … 32 76732-bit signed−2 147 483 648 … 2 147 483 647
16-bit unsigned0 … 65 53532-bit unsigned0 … 4 294 967 295
32-bit float±1.175494e−38 … ±3.402823e+38 (two registers)
  • You infer the type from the map's min/max. A register spanning 0–65 535 is 16-bit unsigned; −1800…1800 (an SEL-751 angle) is 16-bit signed; a HI/LO pair each spanning 0–65 535 is one 32-bit value. This is literally the method AG2022-04 teaches.
  • 32-bit values ride in two registers and the word order is a convention. On the SEL-751, MWH3PI HI at register 380 carries bits 31–16 and LO at 381 carries bits 15–0 — most significant register first. Clients name the choice: the RTAC's Variation column uses LSB/MSB for byte order within a register and LSR/MSR for register order across a 32-bit pair (e.g. SEL-751 energy tags = 32-bit unsigned MSR). The RTAC's default variation is 16-bit signed MSB — change it per tag to match the server.
  • Values are scaled integers. Actual value = register value × the map's multiplier column: SEL-751 angles are ×0.1 (a read of 300 = 30.0°), phase-to-phase voltages ×0.01 kV, energies ×0.001 MWh, power factor ×0.01. The SEL-735 encodes the same idea in its data types — INT×10/100/1000 and LONG×10…10000 scale factors — plus BITMAP, ENUM, and null-terminated STRING types spread across as many registers as needed. Forget the multiplier and everything reads 10× or 100× off.
  • Bits come packed. Read via FC 01/02, coil and input states pack 8 per byte, the starting address in the least significant bit, padded with zeros to fill the last byte. Read via FC 03, an SEL-751 Relay Word row is one register with its 8 bits in the low byte (value 0–255, high byte zero) — row 15 lives at 1760 + 15 = 1775. Read via FC 02 the same bits are individual discrete inputs at row × 8 + bit.

8Exceptions, timeouts, and the protocol's temperament

When a query reaches the server intact but can't be executed, the server answers with the function code's most significant bit set (03h → 83h) and a one-byte exception code in the data field. That's the entire error vocabulary:

CodeMeaningWhat it means in the field
01hIllegal Function CodeFC undefined or unsupported on this device — e.g. FC 0Fh sent to a SEL-700 series relay
02hIllegal Data Addressunsupported address in the data field: off the end of the map, a register for hardware that isn't installed, or writing a read-only/locked register
03hIllegal Data Valuevalue or count out of range, or a malformed request — on SEL relays this is also the code for a bad bit-state or format error
04hDevice Errorthe device is in the wrong state for the request (751/751A return it for coil writes while disabled — the 751 manual adds: or when the breaker jumper isn't installed)
06hBusya resource is busy — retry later
08hMemory ErrorSEL-735: checksum error on stored data

The temperament: strict lockstep request/response. The line is half duplex and the master runs one transaction at a time — send, wait for the reply or the timeout, then send the next. Recovery is entirely the client's job: the RTAC client exposes it as Poll Timeout and Poll Retries (both suspended for broadcasts, which never get replies), with Intermessage Transmit Delay spacing consecutive requests on shared lines.

Symptom → cause, protocol edition

  • No response at all (RTU) → the silent-discard rule: CRC failure, wrong slave address, or wrong baud/parity/stop turning every frame to garbage. SEL relays keep receive-side counters that say which — the 751A exposes NUMRCV, NUMOTH (frames for other addresses), INVADR, BADCRC, and UARTERR at registers 1789–1793 (751: same counters at 1740–1744) — and FC 08h subfunction 0000h is a pure echo test of the channel.
  • Exception 02h on a documented address → the map varies with installed hardware (the 751 and 751A only answer for cards that are present), or the address is right and the offset convention is wrong (§5).
  • Values plausible but wrong → variation mismatch: signed read as unsigned, HI/LO register order flipped on a 32-bit pair, or the multiplier not applied.
  • Everything shifted by one register → 0-based vs. 40001-convention (§5). The most common Modbus commissioning defect there is.
  • TCP connects then dies, or won't connect → session limits (§2/§4) and idle timeouts are per-device policy, not protocol — check the server's session count and timeout settings before the network.
