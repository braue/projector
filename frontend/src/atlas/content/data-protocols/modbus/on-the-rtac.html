Modbus on the RTAC

Client and server in the SEL-5033 project — sessions, polls, HREG tags, the Variation column, shared server maps, and where the data actually stalls

☰The rules, stated plainly

  • RTAC Modbus is 0-based, always. A third-party map's "40001" is holding register 0 in the project; the legacy 3X/4X prefixes are documentation only and never configured. If the vendor's table is 1-based (many are), subtract 1.
  • One poll = one contiguous range. Every register in the range must exist on the device or the whole poll fails with an exception response — no partial data. Noncontiguous data means multiple polls.
  • The default Variation is 16-bit signed MSB. The RTAC does not know what the server sends; you must set size, sign, and byte/register order per tag to match the vendor map.
  • Nothing flows by itself. Client tags and server shared-map tags are separate databases; the Tag Processor (or Simple Tag Mapper) moves data between them — and scaling lives there too, because the Modbus columns have no multiplier field.
  • Each Modbus server instance accepts one client connection at a time — "connect and stay connected". More masters means more server instances (same shared map).

1Where the RTAC talks Modbus

Southbound, as client: polling legacy meters, third-party IEDs, RTUs, and communications processors that only speak Modbus — the RTAC stores the polled values in its database for logic, logging, and re-serving in richer protocols. Northbound, as server: answering a SCADA master, third-party HMI, or comm processor that polls the RTAC itself. The RTAC supports Modbus RTU (serial), Modbus/TCP, and Modbus RTU tunneled over Ethernet; Modbus ASCII is not supported. Function codes 01h–06h, 0Fh, 10h, and 11h (Report Server ID) are implemented on both ends.

2Client: the session and device settings

Insert ► Other ► Modbus (or right-click Devices ► Add Other Device ► Modbus Protocol). Give the device a unique name — it becomes the prefix of every tag — and pick the connection type:

Connection typeUse for
Client–Serialpoint-to-point EIA-232/422/485 to one IED
Client–Multidrop Serialseveral IEDs on one serial port — insert one client per IED, same port number, unique server address each
Client–EthernetModbus TCP; each IED's IP + port combination must be unique
Client–Ethernet Tunneled (Multidrop) SerialRTU frames in TCP through a serial port server; one client per IED, same SPS IP, per-IED port/address
  • Server Modbus Address — the remote server's unit ID, 1–247 (248–255 reserved on serial). Address 0 makes this a broadcast client: write-only, no polls issued, responses not expected, so Poll Timeout / Poll Retries are ignored and the Intermessage Transmit Delay setting is what spaces requests on the multidrop line. The broadcast client's Offline pin generally stays False — don't use it for health.
  • Serial parameters — set Baud Rate to the device, Serial Communications Port Type to EIA485/422 when on 485 (with Full Duplex := False for two-wire), and Serial Communications Port to the physical port (e.g. Port 17, the isolated terminal-strip 485 port on an SEL-3530).
  • Timeout behavior — Poll Timeout and Poll Retries govern each request; the advanced Communications Offline Timer (default 10 s) drives the device's Offline POU pin when nothing is heard.
  • Use Shared TCP Connection (advanced, R155+) — multiple Ethernet clients aimed at the same IP:port each open their own socket by default, which can exhaust a port server's listening ports; enable this on each client sharing the IP:port to round-robin them over one TCP connection.

Polls and tags are configured separately and must agree. On the poll tabs — Read Coil Polls, Read Discrete Input Polls, Read Holding Register Polls, Read Input Register Polls, plus a Report Server ID Poll (FC 11h: server ID, run indicator, vendor data) — each row is Poll Number, Starting Address (0-based), Quantity, and Poll Period in ms. Slow-changing data can poll lazily (a meter's model number every 9000 ms) while measurements poll fast (2000 ms) — per-poll periods are how you spend serial bandwidth where it matters. Limits per query: 125 registers, 2000 bits.

On the tag tabs (Coils, Discrete Inputs, Holding Registers, Input Registers; 30,000 tags per type, 5,000 on an SEL-3505) each tag gets an address plus type columns. Defaults are unhelpful on purpose: tags come named HREG_xxx / DI_xxx with contiguous addresses from 0 — rename every tag to what it means (IA_MAG, not HREG_002) and set the real addresses from the vendor map. Ctrl+C/Ctrl+V pastes whole columns of names from a spreadsheet. Create only the tags you need; every tag costs processing.

  • Analog columns — Dead Band: when |instMag − mag| exceeds it, mag updates and the RTAC generates a timestamped event; dead band 0 = an event for every value received, same trap as DNP. Zero Dead Band forces small values to 0; HH/H/L/LL limits generate alarms; Min/Max clamp the point.
  • Control Value (holding registers) — the default value the RTAC will write to the IED in a write-holding-register message, before logic overwrites it.
  • Coils tab — the coil's bit address "you want to operate": client coils are write points (FC 05/0F), discrete inputs are the read side.
The poll must cover the tags, and the device must cover the poll. Tags only fill from polls whose range includes their address — a tag outside every poll just sits at its default with no error. And if any register inside a poll's range doesn't exist on the device, the server rejects the entire poll with an exception response. When one value is missing, check both directions.

4The third-party-device workflow

SEL's worked example (AG2015-32, Eaton IQ 250/260 meter on two-wire EIA-485) is the template for integrating anything with a vendor register map:

  • Read the vendor map first. Note which spaces exist at all — the IQ 250/260 serves only holding (4X) registers, so everything goes in the Holding Registers tab and FC 03 polls, whatever the data "is".
  • Fix the addressing base. The Eaton map is 1-based: its registers 1000–1001 (Volts A-N) are RTAC addresses 999–1000. Subtract one from every documented address. (Some vendors document 0-based, some 40001-based — establish which before typing anything.)
  • Match the format per point. The voltages are 32-bit floats: Tag Type APC (so the tag can carry float values), Variation 32-bit Float MSR (most significant register first). Save, and Register Address Stop auto-fills to start+1 — 32-bit tags consume two consecutive registers, and the address auto-numbering skips accordingly. The meter-type register stays a plain 16-bit read.
  • Split polls along the map's gaps. The map isn't contiguous, so: one poll at address 16, quantity 1, period 9000 ms (model number — never changes); one poll at 999, quantity 6, period 2000 ms (three floats × two registers).
  • Verify online against the device's own display. Go online, watch the tags, and compare with the meter front panel (for an SEL relay: MET / MET E / TARGET responses). Values present-but-wrong at this step are almost always Variation (sign or word order) or an unapplied multiplier — §5.

Physical-layer footnote from the same guide: the RTAC's terminal-strip 485 port is four-wire full duplex — jumper +TX/+RX and −TX/−RX (or use an SEL-C691 cable, jumpers built in) for two-wire devices, and set Full Duplex := False. Signal ground goes to the Shield terminal; cable shield drain grounds at one end only.

5Data types: Variation, word order, scaling

The Variation column is where Modbus's "everything is 16 bits" meets reality. It sets size, sign, and swap for each tag:

Variation familyMeaning
16-bit signed / unsigned, LSB / MSBone register; LSB/MSB choose byte order within it. Default: 16-bit signed MSB — wrong for unsigned points like current magnitudes
32-bit signed / unsigned / float, LSR / MSRtwo consecutive registers combined into one tag; LSR/MSR choose which register is least/most significant
  • Tag Type carries the value; Variation decodes the wire. MV/INS-style analogs for plain reads, APC where floats or setpoint writes are needed, STR (with Number of Bytes) for strings, SPS with a Bit Reference to pull one bit out of a packed input register, MDBC to unlock Bit Reference on a holding register and dissect it bit by bit.
  • Packed bits, three ways (AG2022-04, SEL-751 Relay Word): read FC 02 discrete inputs at address row×8+bit; or read the row register via FC 03 as an analog (PB05 asserted in row 15 → register 1775 reads 8); or read the same register with Tag Type MDBC + Bit Reference 3 and get a clean boolean tag. One 16-tag trick: sixteen SPS input-register tags, all at the same address, Bit Reference 0–15 — the RTAC dissects one register into sixteen status points.
  • Scaling is yours to apply. SEL relays (and most vendors) send scaled integers — VBC 2163 means 21 634.6 V (kV × 0.01), MWH3PO 2 313 729 means 2 313.729 MWh (× 0.001). The Modbus tag columns have no multiplier field: apply it in the Tag Processor with a math expression or the SCALE_MV function block (instMag × SCALE + OFFSET, which also carries the source's time and quality through).

The same two raw registers through the right and wrong register-order settings. MSR joins high-then-low into 2 313 729, scaled to 2 313.729 MWh; LSR joins them backwards into 1.31 billion — no downstream scale can rescue a bad join. ▶ Animated in the HTML edition.

6Writes and controls from RTAC logic

Modbus has no SBO, no CROB, no verbs — the manual's phrase is that Modbus "lacks the complex control structure of DNP," so a control maps as one Tag Processor entry per point. The write machinery on the RTAC client:

  • Coils → MDBC (Modbus Coil Control): a structure with operSet and operClear, each carrying ctlVal (BOOL) plus a pulseConfig, and a status SPS. Trigger the operate and the client issues the coil write (FC 05/0F). Because MDBC is a command-style type, the Tag Processor and Simple Tag Mapper auto-convert richer controls onto it: a DNP master's close / latch-on becomes operSet, trip / latch-off becomes operClear, and a DNP pulse maps to operSet (Auto mode) — so SCADA trip/close commands can land on a Modbus-only device with one mapped row.
  • Holding registers → APC (Controllable Analog Set Point): a rising edge on oper.trigger sends oper.setMag to the device as a register write. The tag column Control Value supplies the default written value before logic touches it.
  • Broadcast writes: a client at address 0 sends coil/holding-register writes that every listening server on the multidrop executes, with no responses and no retries — space them with Intermessage Transmit Delay (§2).

On the server side, an incoming FC 05/06/0F/10 from the master lands on the shared-map coil or holding-register tag; your Tag Processor rows or logic carry it onward to the field device. The server device's Disable_Controls POU pin blocks all coil and holding-register writes — and because it acts on the shared map, it disables controls for every server instance sharing that map.

7Server: shared maps and sessions

Building the served map

Since firmware R153, tags live in a Modbus Server Shared Map (Insert ► Tag Lists, or Add Tag List ► Modbus Server Shared Map; up to 120 per project), not on the server device. The map has tabs for Discrete Inputs, Coils, Input Registers, Holding Registers — you assign each tag a 0-based address in its space, then set the server device's Map Name setting to the map. Multiple server instances can reference one map and present identical data. Columns mean the same as on the client side with two inversions: Bit Reference now selects which bit of the served register a value populates (build packed registers for the master out of individual booleans), and CMV tags gain served angle fields. The Tag Processor populates everything — an empty map serves defaults forever.

Map layout discipline. The RTAC is the one device in the yard whose Modbus map you design — so design it: group everything the master needs into one contiguous block per register type, in a stable order, so the master reads it in one FC 03 of ≤125 registers. You are building for someone else exactly the convenience the SEL relay user map builds for you (see Modbus on SEL Relays). Leave spare addresses between logical groups for growth; never renumber a live map.

Sessions and addressing

  • Connection types mirror the client list: Serial, Multidrop Serial (RTAC as one drop on a 485 loop, unique ID), Ethernet (Modbus TCP), Ethernet Tunneled (Multidrop) Serial (RTU in TCP). Ethernet servers take a comma-separated allowlist of up to 20 client IPs, or allow anonymous connections.
  • One client connection per server instance, designed for connect-and-stay-connected. A second master isn't queued — give it its own server instance.
  • Server MODBUS Address is 1–247 or 255 = answer any unit ID (fixed at 255 before R153). Two sanctioned ways to share one TCP port among anonymous servers: (a) unique addresses 1–247 — one client round-robins them by unit ID, emulating a port server in front of a multidrop RTU chain; (b) several address-255 servers all referencing the same shared map — incoming connections are handed to the next free server, so the collection looks like a single Modbus server that accepts simultaneous clients. Otherwise each anonymous server needs its own port.
  • POU pins (Table 2.117): inputs EN, Disable_Controls, Disable_Tag_Updates (both act map-wide), Reset_Statistics, Communications_Offline_Timer (default T#10000MS); outputs ENO, Offline, Illegal_Data_Address / Illegal_Data_Value / Illegal_Function_Code (assert ≥1 processing interval when a client asks for something invalid), Message_Failure(_Count), Message_Success_Count, Messages_Received_Count, Messages_Sent_Count, Direct_Transparent_Connection.
Contrast with the DNP3 server: the Modbus server has no event queues, no classes, no SOE buffering, no timestamps, no unsolicited — the master gets whatever is in the map at the instant it polls, full stop. Anything event-shaped must be served over DNP3 instead (see DNP3 on the RTAC); the Modbus map is for masters that only do registers.

8The Tag Processor seam

Client tags and server maps never touch directly: every value crosses through the Tag Processor (or Simple Tag Mapper) as a Destination ← Source Expression row, and the destination inherits the source's value, quality, and time. That's how a southbound comm failure surfaces northbound — the offline device's now-invalid data carries its quality into the served tags. Controls run the seam backwards, and their quality flows server→client: an IED's control tag inherits invalid quality when the server connection is down even though the client link is fine. Source expressions take math (scaling, §5) and IEC 61131-3 fragments. Details on the RTAC platform pages — this seam behaves identically for every protocol pair.

9Troubleshooting from the RTAC side

Symptom → cause

  • Device Offline, tags invalid → serial: wrong Server Modbus Address, baud/parity, port type not set to 485, two-wire loop without Full Duplex := False, TX/RX jumpers missing. RTU failures are silent — a wrong address or bad CRC produces no reply at all, just Poll Timeout → retries → Offline. TCP: wrong IP/port, or the far end already has its one allowed connection. Note Offline = False does not prove data flows — a settings mismatch can hold the link "up" with nothing usable exchanged.
  • Whole poll returns nothing, device online → one nonexistent register inside the poll range; the server answers with an exception and the RTAC gets no data for any tag in that poll. Shrink the poll until it works, or split per the vendor map. (Debug trick from AG2022-04: temporarily use one poll per tag so each failure names its register.)
  • Tag never updates, no errors anywhere → its address isn't covered by any poll, or the tag/poll is on the wrong function-code tab (holding vs. input registers).
  • Values present but wrong → Variation: sign (default is signed MSB), byte order, or LSR/MSR register order on 32-bit tags (§5); or the vendor multiplier was never applied in the Tag Processor; or a 1-based vendor map entered without the −1, putting every tag one register off.
  • Server ignores a master → master's IP not in the allowlist, another client holds the single connection, unit ID mismatch against a 1–247 server (use 255 to answer regardless), or two anonymous servers colliding on one port outside the two sanctioned patterns (§7). Watch Illegal_Data_Address/Illegal_Function_Code pins: they assert per offending query and finger the master's map or FC assumptions.
  • Polling mysteriously stopped → a direct transparent access-point session (third-party software configuring the IED through the RTAC) suspends Modbus polling on that port for the duration; polling resumes when the session ends. The server-side pin Direct_Transparent_Connection shows it live.

Instruments

  • Statistics pins — every Modbus device exposes counters (Messages_Received_Count, Messages_Sent_Count, Message_Failure_Count, Message_Success_Count) plus Offline; read them in logic or the web interface, clear with Reset_Statistics. Failures incrementing while successes climb = intermittent line, not configuration.
  • Online Packet Dissector (R151+, SEL-3555/3560/3350) — Web interface ► Connected IEDs ► select the device ► Actions ► Inspect Packets. Live decode of serial and TCP Modbus with Wireshark display-filter syntax: modbus shows all Modbus traffic, modbus.func_code == 3 isolates holding-register reads — exception responses and their codes appear decoded in the tree. On other models, capture a pcap from the same page and open it in Wireshark.
  • Live Data / Tags view — watch the client tag against the device's own display (meter front panel, relay MET/TARGET); the manual's own diagnostic pattern for value-shape problems.
