☰The rules, stated plainly

Philosophy

  • An SDN switch forwards only conversations you engineered as flow entries. A packet with no matching flow is dropped — deny-by-default, zero trust.
  • No MAC learning, no spanning tree, no broadcast domains. The switch is a look-up table; the thinking lives in the SEL-5056 Flow Controller.

Operations

  • The 5056 is an engineering and monitoring tool, not a runtime dependency: once programmed, switches keep operating (and failing over) with the controller offline.
  • Failover paths are pre-programmed (Fast Failover groups). Healing is measured in microseconds, not RSTP reconvergence time.

1What OT SDN is

Traditional switches decide how to forward (control plane) and forward (data plane) in the same box, using MAC learning and RSTP. OT SDN pulls the control plane out into central software — the SEL-5056 — and leaves the switch as a programmable match-and-action look-up table. SEL's user guide is explicit that "the OT SDN underlay control plane replaces the legacy RSTP managed switch control plane." OpenFlow 1.3 is the language between controller and switch; STP and dynamic MAC learning are removed entirely.

Every allowed conversation is a flow entry: match fields (which packets), instructions/actions (what to do with them), and counters (proof it's happening). You engineer flows ahead of time — proactive traffic engineering — including the backup paths for every failure, so nothing has to converge after a fault. What you get, per the UG: deny-by-default network access control with Layer 1–4 packet inspection at every port, sub-millisecond network healing, and the certainty that each host receives exactly the traffic you provisioned and nothing else.

A destination MAC starting 01: no longer means "multicast to everyone on the VLAN." You decide where a GOOSE frame goes, per subscriber, per circuit — micro-segmentation down to individual conversations, with no VLAN management overhead (SEL-5056 IM).

2SDN vs. RSTP/MAC-learning — the honest contrast

Same three-switch network, two philosophies. RSTP discovers a topology and reacts to failures; SDN is told a topology and has the reactions pre-programmed. (For the RSTP side in depth — root bridges, ring/ladder sizing — see RSTP & Topologies in atlas.)

3The pieces

SEL-5056 Flow Controller

Central software (Windows Server 2022 or SEL Blueframe; browser UI) that commissions, configures, and monitors every SDN switch — OpenFlow 1.3 plus REST. Does topology discovery, end-to-end circuit provisioning, and telemetry; can also manage third-party OpenFlow 1.3 switches. Imports IEC 61850 SCD files, RTAC config files, and Visio drawings to automate provisioning.

The switches

SEL-2740S: 20-port modular flagship (6 hot-swappable module slots; rack/panel/surface mount), 8,192 flow entries in 4 tables, 256 groups × 30 action buckets, 4 WRR queues (8:4:2:1), store-and-forward, IEEE 1613 / IEC 61850-3. SEL-2742: 12-port compact/DIN-rail sibling, 8,192 flows, two PoE+ ports (5–6), IEEE 1613. Newer SEL-2731 (24-port, 8,192 flows) and SEL-2741 (24-port, 16,384 flows) run the same OT SDN firmware; the family also includes the 2743 (8-port) and 2744 (10-port).

Adoption — how a switch joins

Out of the box, a switch publishes an OpenFlow discovery packet (LLDP-structured, Layer 2) every few seconds announcing its default IP — front port ETH F in 169.254.x.x/16, data-plane ports in 192.168.x.x/16 (last two octets random). The 5056 commissions it over REST (port 443): IP, time, certificates, controller address. The switch then connects to the controller on TCP 6653 (OpenFlow, TLS with X.509). "Adopted" = connected on both interfaces. A switch pairs with one controller and stops advertising; re-homing it requires a factory reset (pinhole button or controller action).

Controller offline ≠ network down

Flows are stored in the switch and retained through power cycles even with the controller offline (SDN UG). Per the 5056 IM: once configured, the controller "no longer needs to be online for proper network operations" and "is not a single point of failure." Offline you lose engineering, monitoring, and host discovery — not forwarding or failover. Exception: flows with idle/hard timeouts are deleted on switch reset or power cycle.

4Flows in depth

A flow entry = general settings (flow ID, table, priority 0–65535, idle/hard timeout) + match fields + instructions + counters. On ingress, table 0 is searched; a Goto-Table entry chains the search through all four tables. Highest-priority match wins (the 5056 checks for overlapping flows and flags them). No match anywhere → the packet is dropped.

Every present match field must match for the entry to match; absent fields are wildcards. More fields = more exclusive; masks widen a field back out.

Instructions, actions, groups

  • Instructions (applied in order): Meter (rate limit), Clear-Actions, Write-Actions, Goto-Table.
  • Actions inside Write-Actions: PopVlan, PushVlan, SetVlanId, SetVlanPcp, SetQueue (1–4), Group, Output. If no Output action ever executes against a packet, it's dropped.
  • Group types: Indirect (port aliasing — change one Output instead of every flow), All (replicate to a set of ports — how multicast fan-out is built), Select (round-robin link aggregation), Fast Failover (ordered buckets with liveness — the redundancy mechanism, §6).
  • Table-miss entries (priority 0, no match fields) catch everything unmatched. The 5056 installs four of them — ARP, GOOSE, SV, other — that send rate-metered copies to the controller for host discovery; delete/disable them if you don't want discovery. A table-miss with no Output drops the packet.
  • Priorities to respect: the 5056's own commissioning flows sit at 0, 1, 60000, and 65000 (aliases starting SEL-5056:). Keep user flows between 2 and 59999 — 100–64000 recommended. Protocol default is 2000; SEL recommends ≥15000 for GOOSE and SV so they land in flow table 0 (lowest latency).
VLANs, repurposed. Segmentation doesn't need VLANs here — there are no broadcast domains. But the system quietly uses VLAN tags to "color" packets in flight (applied at the first switch, stripped at the last, up to three tags). Use the 5056's VID reservation feature so your real VLAN IDs (e.g. tagged GOOSE from relays) never collide with the automation's designation tags.

1 · DesignDraw topology + hosts (online or offline, even before hardware) — UI, Visio import, or Network Builder CSV; import SCD/RTAC files
→
2 · Discover & adoptSwitches self-announce; auto-adopt when physical matches design (mismatch blocks adoption), or adopt manually
→
3 · Provision circuitsSource + destination(s) + protocol; path planner derives flows, groups, redundancy on every switch
→
4 · Verify & baselineCircuit status, SAT report, difference report vs. drawings, counters
→
5 · OperateTelemetry every 10 s, Syslog, taps; controlled change management
  • Circuits, not switch logins. A circuit is one communications channel: one source, one or more destinations (multicast only), one protocol. You never configure individual switches — the path planner works out which switches need which flows, end to end.
  • Protocols are reusable match profiles — e.g. HTTPS = EthType IPv4 + IpProto TCP + TcpDst 443. Bidirectional (TCP) circuits get the reverse-direction flows generated automatically. Per-protocol options: Proactive Failover (redundancy at each hop — SEL says keep it on), source-address matching, MAC Address lock (so an authorized IP device can't be silently swapped), egress queue (Critical/High/Medium/Low), hard timeout.
  • Applications create and manage circuits in bulk from host profiles (recommended over one-at-a-time circuits); SCD import auto-provisions all MMS, GOOSE, and SV circuits from the same file that programmed the relays.
  • Statuses tell you what's real: Controller Status = the path planner planned it; Switch Status = the flows are actually programmed (offline designs sit at Pending until switches sync). Replan after topology/port changes re-derives paths with minimal disruption.
  • Testing: the Site Acceptance Test report lists every circuit as source port / destination port / switch ports / exact match fields — one row per port combination — a complete test checklist. The Usage Statistics report tracks flow/group/meter headroom per switch (warns at 90%). Network Builder difference reports diff a proposed build against what's deployed — your drawings become the configuration baseline.

6Failover — pre-programmed, not reconverged

Redundancy is compiled into each circuit at provisioning time. The first switch's flow points at a Fast Failover group: an ordered list of action buckets, each watching a port (or group) for liveness. The packet goes to the first live bucket; if the primary link is down, the very next packet takes the backup bucket's path. No election, no BPDUs, no learning — the SDN UG rates healing at less than a millisecond, and the 2740S/2742 manuals say faults heal "in microseconds." If no bucket is live, the packet is dropped.

Both paths exist in the switch before the fault. Failover is bucket selection by port liveness — the controller is not consulted and doesn't need to be online. ▶ Animated in the HTML edition.

7Why this suits protection traffic

  • GOOSE and Sampled Values are deterministic here. Multicast is delivered only to provisioned subscribers over known paths with known backups — no flooding, no reconvergence gap during a fault. SEL positions OT SDN for "even the most demanding Ethernet communications, such as IEC 61850-9-2 sampled values." Give GOOSE/SV protocols priority ≥15000 (flow table 0) and a high egress queue. Mechanics of GOOSE itself: see IEC 61850 GOOSE in atlas.
  • Per-circuit QoS without tags. The egress queue is set by flow, not by VLAN PCP — untagged traffic still gets priority treatment, per conversation.
  • PTP-aware: switches are IEEE C37.238-2017 Power Profile P2P transparent clocks (disabled by default); provision PTP as a multicast circuit to every clock, client, and switch.
  • PRP interplay: the 5056 supports PRP port groups (dual-connected hosts) and the switches protect against singly-attached-node flooding — see PRP, HSR & Redundancy in atlas.

8Operational care & monitoring

  • Plug in an unplanned device → nothing happens. Its frames match no flow and are dropped (host-discovery table-miss may report it to the controller). Every new conversation — a test set, a vendor laptop — needs a circuit first. Plan for this during commissioning outages.
  • Make the denial visible: unplanned traffic taps forward unmatched traffic to a tap destination (e.g. an IDS), rate-metered, optionally VLAN-tagged per switch+port (starting VID + port number) so you can see exactly where it entered. The alarm contact can be set to latch if an unused port ever links up.
  • Timed conversations: hard-timeout circuits (0.0–18.2 h) auto-disable in the switch even with the controller offline — SEL's pattern for remote vendor access and rarely-used, higher-risk circuits.
  • Counters everywhere: per-port packets/bytes, per-flow packets/bytes/duration, per-group and per-meter counts. A circuit's View Flows shows its counters — a flow at zero while the publisher publishes is your mis-match clue; Reset Traffic zeroes them for a clean test.
  • Circuit taps mirror any conversation to any port on the network (with optional redundancy and metering) — no dedicated mirror-port infrastructure.
  • Change management is transactional: with Active Configuration off, changes queue as synchronization events you authorize deliberately. Modify in-band-management flows farthest-from-controller first, one at a time.
  • Logs: switches store 4,096 events locally and Syslog (UDP or TLS) to up to three servers; the 5056 also collects everything centrally. SNMPv2c/v3 is read-only. OpenFlow changes batch into single log lines (Fa/Fd/Fm… + hex IDs, 10 s intervals).
  • Replacement is an adoption action: the 5056 holds every switch's configuration; Replace programs a factory-fresh unit before or after physical install.
The trade: everything must be engineered — there is no "just plug it in." The discipline that makes the network secure and deterministic is the same discipline that makes an unplanned addition a change-management event, not a field improvisation.

9Troubleshooting & fine print

  • Two devices can't talk → no circuit, or the protocol's match fields don't fit the real packets (wrong EthType/port, unexpected VLAN tag). Check the circuit's flow counters — zero hits means the match is wrong or the traffic isn't arriving.
  • Circuit shows Controller Status Success, Switch Status Pending/Failed → switches offline or out of sync; synchronize (SEL suggests trying twice if an event won't clear) and read the per-setting rejection error.
  • Gigabit copper failover feels slow → the standards-mandated 720 ms link-down wait is still enabled; disable it (Gigabit Copper Fast Failover).
  • Switch won't adopt to a new controller → by design; factory-reset it first — pinhole button, an assigned digital input (asserted 5 s), or from the current controller.
  • Flow table pressure → run the Usage Statistics report; enable flow compression on circuits; remember deleting a group/meter deletes every flow referencing it.
