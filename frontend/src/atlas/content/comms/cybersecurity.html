☰The rules, stated plainly

Substation security

  • Change the default passwords at installation. Every SEL relay ships with published defaults (OTTER/TAIL/…) and the manuals warn in bold that leaving them invites unauthorized access.
  • Relay access-level passwords are shared accounts by design — no audit trail of who used them. A security gateway's proxy replaces them with per-user credentials and logs every command.
  • The gateway firewall is deny-by-default: no rule, no traffic. Rules process in priority order; the first match wins.
  • Every layer should log. Gateway → Syslog + Commands and Devices report. Relay → SALARM pulse on failed/elevated access, SER for event history.

1The threat model, in field terms

The substation's exposure is mostly its engineering access paths — the same serial ports, Telnet sessions, and dial-ins engineers use for settings work. The 3610/3620/3622 manual frames the classic problem plainly: to touch a relay you log in to a global shared account ("Access Level 1 for read-only, Access Level 2 for read-write"), so the password must be shared among everyone, and there may be no audit trail beyond changed settings or an alarm-contact pulse.

  • Serial went routable. The SEL-3610/3620 convert serial DNP3 and Modbus to Ethernet (Raw TCP/UDP encapsulation, Modbus TCP) — the manual's job examples even run DNP3 over cellular. Yesterday's null-modem cable is now a network path, which is exactly why the same boxes carry a firewall and VPN.
  • People, not just attackers. The gateway's account features target insider/lifecycle risk: disable accounts during extended leave, delete them on departure ("to prevent security breaches"), and every account change is logged with who made it.
  • Physical access at remote sites. The SEL-3622 is built for small remote enclosures where "physical access can be a bigger concern" — accelerometer, light sensor, and input contact detect tampering.
  • Plaintext legacy protocols. The SEL-751A's Ethernet services are Telnet and FTP; the SEL-751 adds an HTTP web server (on by default) and IEC 61850 MMS; serial ports speak SEL ASCII, Modbus, DNP3 — none encrypted. The 751 manual says it itself: FTP, HTTP, and Telnet "do not inherently support message encryption" and recommends a security gateway plus SEL SDN. Protection has to come from the layer in front (SSH/IPsec on the gateway).

2Defense in depth: the layers

No single control carries the weight. The documented stack: physical (locks, tamper sensors) → network segmentation (VLANs, routing) → gateway (firewall, VPN, user auth) → device access levels (passwords per level, port restrictions) → logging (Syslog, reports, SER, alarm contact). An intruder has to beat all of them; a legitimate engineer passes through all of them leaving a trail.

3Relay access levels: the 751/751A / 451 model

SEL relays gate every command behind a hierarchy of access levels, each with its own password. On the SEL-751 and SEL-751A the ladder is 0 → 1 → 2 → C (identical levels, prompts, and defaults); the SEL-451 (400 series) splits the middle into job-specific levels so a switching operator never needs the settings password.

751/751A levelPromptEnter withWhat it allowsDefault password
0=(connect) / QUITA few commands only (incl. what comms processors need); first layer of securitynone — no password to descend

On the SEL-451 the levels are 0, 1, B, P, A, O, 2, C — entry is sequential (Level 1 first, then any xAC command): ACC→1 (OTTER), BAC→B breaker control (EDITH), PAC→P protection settings (AMPERE), AAC→A automation settings (VOLTA), OAC→O output settings (WATT), 2AC→2 everything (TAIL), CAL→C from Level 2 only (Sel-1). The manual's advice: set unique passwords for each access level so breaker, protection, automation, and settings duties are separately credentialed.

Failed attempts, timeouts, and the ALARM contact

  • 751/751A: three wrong passwords → the relay pulses SALARM for one second and stays at Access Level 0. SALARM also pulses on successful Level 2/Level C entry (or denial), on settings changes, group changes, and password changes — and the factory default output equation is OUT101 := HALARM OR SALARM, so all of it reaches the alarm contact SCADA watches. (751 R402+ also locks the IEC 61850 MMS server out after three failed passwords within a minute.)
  • 451: third failed attempt → asserts BADPASS and SALARM for one second, prints "ACCESS BY UNAUTHORIZED PERSONS STRICTLY PROHIBITED", blocks further attempts for 30 seconds, and on Ethernet/DNP3/Mirrored Bits virtual-terminal connections terminates the connection. SALARM also asserts whenever B/P/A/O/2 is entered from a lower level.
  • Timeouts drop you back down. 751/751A serial: after T_OUT minutes idle at Level 2 (0–30, default 5; 0 = never) the port returns to Level 0. Telnet: TIDLE 1–30 min, default 15. Front panel: FP_TO resets to Level 1 and abandons unsaved setting edits. 451 ports behave the same via SET P timeouts.
  • Hardware overrides exist — treat them as physical security. 751/751A main-board jumper A bypasses passwords entirely (the alarm contact still closes on Level 2/C entry; on the 751 the bypass only reaches the port's MAXACC cap); jumper B enables OPEN/CLOSE breaker commands — default off on the 751A, but shipped ON on the 751 — remote bits are always live either way. The 451 offers PAS n DISABLE for temporary unprotected access to a level — same idea in software.

Per-port restrictions

  • 751/751A: every port has EPORT := Y/N (disable unused ports) and a single PROTO (SEL ASCII, DNP, Modbus, Mirrored Bits…) — a port speaks one protocol. On Ethernet, each service is individually gated: ETELNET, EFTPSERV, E61850, EMOD (0–2 sessions), EDNP (751A: 0–3 sessions; 751: 0–5) — all off or minimal unless needed. FASTOP := N (default) blocks binary Fast Operate control messages on that port. The 751 additionally ships an HTTP web server on by default (EHTTP := Y, port 80, own HTTPACC level cap and idle timeout) — unsecure HTTP; disable it or cap it like any other service.
  • 451 and 751 (not the 751A): MAXACC — a per-port cap on the maximum access level, "useful to restrict what remote users can do": a SCADA-facing port can be pinned so no one can ever reach settings through it. On the 751 it is on every serial and Ethernet port (default 2), with separate FTPACC/HTTPACC caps — and even the password-bypass jumper obeys it.
Passwords on the relay: up to 12 characters, any printable ASCII, case-sensitive. Strong per the manuals: all 12 characters, mixed case plus a digit or special character, not a name/date/word (e.g. #0t3579!ijd7). The 451 front panel can only type letters, digits, underscore, and period — keep passwords to those characters if you need front-panel elevation.

4The security gateway: SEL-3610 / 3620 / 3622

Three boxes, one family. The SEL-3610 is a cryptographic port server — 17 serial ports mapped to Ethernet (SSH, Telnet, Raw TCP, Modbus TCP, UDP). The SEL-3620 adds the security core: router, VPN endpoint, stateful deny-by-default firewall, single-sign-on proxy access to IEDs, and automated IED password management. The SEL-3622 is the same gateway shrunk for remote sites — 4 serial ports, low power, physical tamper sensors. All run exe-GUARD whitelist malware protection (always on, R200+) and accept only SEL-signed firmware.

Stateful firewall

  • Deny by default — every connection is refused until a rule explicitly allows it. Rules filter on transport protocol, IP address/group, port/group, and encryption state; actions are Accept, Drop, or Reject (Reject tells the source).
  • Priority order, first match. If the rule list is exhausted, the packet drops. Order matters: a global "allow UDP" above an interface-specific "deny UDP" makes the deny dead — the manual calls this out explicitly.
  • Global toggles: Drop Ping and Drop Traceroute (both on by default), Must Be Encrypted (drop anything outside an established IPsec tunnel), Allow All Encrypted. All firewall configuration changes are logged.
  • NAT (R202+): outbound NAT plus port forwarding (up to 200 entries). Notably, ACSELERATOR RTAC (SEL-5033), web UIs, SNMP, and RDP cannot be proxied — the manual's answer is NAT port forwarding for those.

User-based proxy: killing the shared password

Users connect to a Script-Enabled Master Port (SMP) — SSH, Telnet, Raw TCP, serial, or modem — and log in with their own username and password, verified against local accounts, LDAP, or RADIUS. Groups (Supervisors / Engineers / IT in the manual's example) map to per-IED, per-access-level permissions in the QuickSet Connection Directory: check boxes for CONN, ACC, 2AC, CAL on each relay. Then:

  • WHO lists the devices that user may reach; SEL n connects to one.
  • Typing ACC, 2AC, CAL (also PAC, BAC, OAC, AAC, EAC, EZA, BRE) triggers a script: the gateway enters the relay's stored password itself — the engineer never learns the relay password.
  • PAS is blocked at the proxy ("Command not allowed") — password changes belong to the gateway's password manager, not to users. <Ctrl+W> ends the IED session; KILL aborts a stalled script.
  • Local user store: up to 256 accounts, two roles (Administrator / Technician), enable/disable for leave, delete on departure; passphrases ≥ 8 characters from all four character sets (up to 127, spaces allowed), never displayed or stored in cleartext. Three failed web logins lock the username for 30 seconds and pulse the gateway's alarm contact three times.

Automated IED password management

  • The gateway holds up to three passwords per IED account level: Initial (as first uploaded), Current (on the IED now), Proposed (generated, pending apply) — Generate and Apply are always separate steps.
  • Changes can be manual, scheduled (e.g. every 90 days — "satisfies regulatory password requirements"), or triggered externally (ACSELERATOR TEAM). Covers SEL IEDs, GE Multilin relays, and third-party IEDs with ASCII (or SSH) interfaces.
  • Checkout temporarily reverts an IED to initial passwords for test-set work; check-in restores the secure one. Revert puts defaults back in emergencies.
  • Before any firmware change, settings upload, or Connection Directory upload: download the Managed Device Passwords report (PDF + JSON) to secure offline storage — several documented scenarios can desynchronize ("lose") current passwords.

VPN and encrypted transport

  • IPsec (3620: 16 simultaneous tunnels; 3622: 4; not on the 3610) to another 3620/3622, a Lemnos-compliant device, or a Cisco L3 device; peers authenticate by pre-shared passphrase or X.509 certificate. Combine with the firewall's Must Be Encrypted to force all traffic through the tunnel.
  • MACsec (802.1AE) for layer-2 link protection; SSH for serial tunneling and the SMP; the management web UI is HTTPS with TLS 1.2/1.3 only.
  • Legacy Windows tools that only speak serial/Telnet ride through via SEL-5827/5828 virtual port clients, which tunnel their plaintext inside SSH to the gateway.
Emergency access: if the WAN (and therefore LDAP/RADIUS) is down, you still need in. SEL's documented practice: a local emergency account on every gateway, same name everywhere, strong generated password, changed after each use and rotated regularly "as required by NERC CIP regulations" (App. C; SEL provides sample scripts to automate it fleet-wide).

  • The shared-password problem: relay passwords are per-level, not per-person — everyone with Level 2 duty knows the same secret, and it must be re-issued every time someone leaves. The gateway proxy dissolves this: people carry personal credentials, the gateway alone knows relay passwords and rotates them on schedule.
  • Passwords should never be shared or written down (gateway manual, verbatim). The one sanctioned exception: the Managed Device Passwords report kept offline in secure storage for disaster recovery.
  • Both relay manuals carry the same boxed warning: change default passwords to private ones at installation; SEL disclaims damage from unauthorized access if you don't.

The pattern: terminate the encrypted session at the gateway, let the last plaintext hop be a serial cable or a switch port inside the protected zone. That is the architecture the 3610/3620/3622 manual is built around.

7Logging & monitoring: proving who did what

Gateway records

  • Syslog (RFC 5424): 60,000 events in nonvolatile storage (oldest overwritten), forwarded to up to 3 remote servers / SIEMs (Splunk, QRadar, LogRhythm named). Seven severities (informational→emergency), four facilities (Kernel, User, System, Security), IRIG-B/NTP timestamped. Covers logins, config changes, firewall changes, exe-GUARD violations, IPsec changes.
  • Firewall verbose logging: every connection established/closed/dropped/rejected with protocol, source/dest IP:port, and action (Off / Blocked / All / Custom per rule, R208+). Watch the 60k limit on noisy networks.
  • Commands and Devices report: every ASCII command run through the SMP — user, command, source IP or COM port, UTC timestamp to the second. PDF + JSON, up to 20,000 events per report, optional encryption. This is the audit trail shared relay accounts never had.

Relay records

  • SALARM → alarm contact: access-level entries, three failed passwords, settings and password changes all pulse SALARM, and OUT101 := HALARM OR SALARM by default — SCADA sees a contact close within seconds of someone knocking on the relay.
  • SER: assign SALARM (751/751A default: SER4 := SALARM) and security-relevant Relay Word bits to the Sequential Events Recorder for a timestamped on-relay history — see SER & SOE in atlas.
  • 451 extras: BADPASS Relay Word bit for failed password attempts — usable in SELogic and SER like any other bit.

Compliance drivers (only as far as the docs go)

  • exe-GUARD whitelist protection "helps support NERC CIP compliance efforts" (built with DOE, Dominion, Sandia).
  • Emergency-account passwords must be "changed regularly as required by NERC CIP regulations."
  • Scheduled password rotation with complexity enforcement "satisfies regulatory password requirements, and ensures that no weak or default passwords are in use." The manuals cite no clause numbers — audit specifics live with your compliance team, not in the IMs.

8Troubleshooting & fine print

  • Proxy is authorization, not a wall: a user without permission to a level "will still be granted access, if they have knowledge of the access passwords of the device" — unmatched input passes straight through to the IED. Password management (so nobody knows the passwords) is what closes that hole.
  • Binary mode bypasses scripting: in SMP binary transfer mode everything except <Ctrl+W> goes straight to the device — use only where required (GE relays, Modbus).
  • Firewall rule "works on one interface, not another" → check rule priority in Integrated View; a higher-priority global rule may be eating the packet first.
  • Locked out of a relay at Level 2? Wait out the timeout (T_OUT/TIDLE drops the port to Level 0) — that's the feature working. Forgotten relay passwords with no gateway record: 751/751A jumper A bypasses passwords locally (physical access required, alarm still pulses; the 751 bypass stops at the port's MAXACC).
  • QuickSet Connection Directory uploads: use a dedicated quickset Technician-level account (one login per account at a time on the web server) and keep usernames/groups exactly matched — case-sensitive — between Device Manager and the gateway.
  • RTAC users/LDAP internals are their own topic — see RTAC Users, Security & LDAP in atlas. This page covers the substation-wide picture and the relay/gateway ends.
