Subnets, CIDR, default and primary gateways, static routes — and where names actually matter on RTACs and relays

☰The rules, stated plainly

Addressing

  • Same subnet = talk directly. Different subnet = talk through a gateway. Every one-way-comms mystery starts here.
  • A device needs a default gateway configured the moment anything off its subnet must reach it — no gateway, no reply.
  • On a multi-port RTAC, one interface's gateway is marked Primary — that's the router used for traffic the RTAC initiates off-subnet.
  • One subnet per interface. Two NICs on the same subnet (with one unplugged) silently eats traffic.
  • Don't set unused Ethernet ports to an active subnet. Disable what you don't use.

Names

  • Substations run on static IPs. DNS is for the RTAC reaching out — NTP by name, email, LDAP — not for SCADA polls.

1Addressing: subnets and gateways

An IPv4 address plus its mask (CIDR) splits the world into my subnet and everything else. Traffic to the local subnet goes straight out the wire; traffic to anything else goes to the default gateway — the router's address, which must itself be on the local subnet. The RTAC states it plainly: packets matching the configured mask route directly; everything else is attempted via the default gateway, if configured.

The classic failure: SCADA's poll arrives (the router knows the way in), but the RTAC has no gateway for the way back — connections half-open, pings one-way. ▶ Animated in the HTML edition.

  • CIDR is just the mask: /24 = 255.255.255.0 (254 hosts), /25 = .128, /30 = .252 (a 2-host link). The 5033 manual carries the full /0–/32 table.

Two devices with the same address but different masks will disagree about whether they are neighbours — and only one of them will be able to reach the other. (Animated in the browser.)

  • Primary Gateway: on a multi-interface RTAC each NIC can define a default gateway, but exactly one is flagged Primary — the router the RTAC uses when it initiates traffic to another subnet. Incoming off-subnet traffic on any interface needs that interface's gateway configured for the replies.
  • Static routes override the default gateway for specific destinations — the common substation case is multiple routers with IEDs behind each: Remote Network (single IP or CIDR range) + Remote Gateway + interface. (R154+ allows a route whose gateway is initially unreachable, for runtime IP-alias tricks — use with caution.)
  • One subnet per interface. The 5033 manual's own worked example: three NICs on 10.201.10.x/24, one of them unplugged — the RTAC sends some traffic to the dead port and it's simply lost, because any same-subnet interface is a "valid" path. Different subnets per NIC, or bridge the ports if you want them switched.

2Names: hostname, DNS, and the hosts table

Substation SCADA runs on static IPs — the DNP client polls 10.20.1.21, not feeder-relay-3.example.com. DNS earns its place when the RTAC has to reach out:

  • Hostname + DNS Suffix form the RTAC's fully qualified name (myRTAC.ad.mynetwork.com) for humans browsing to it.
  • Primary / Secondary Nameserver are the resolvers the RTAC queries — needed when NTP servers are entered by name, for the DAC/event emailer's SMTP host, and for LDAP authentication.
  • The Hosts table is the no-DNS escape hatch: static name→IP entries on the RTAC itself (the manual calls it out specifically for LDAP configuration). If the network has no resolver, put the names you need here.

Design habit: nothing on the SCADA path should depend on DNS. If a resolver outage can stop polls, controls, or time sync, the design is wrong — names are for management-plane conveniences, IPs are for operations.

3RTAC interface checklist

Per-NIC, everything is deliberate — the defaults are conservative and several "it's dead" symptoms are just a disabled service:

  • Per-interface enables: NIC itself, ping, web access, database (ODBC) access, EtherCAT dedication — each per port. A NIC with ping disabled looks down to your laptop and isn't. EtherCAT-dedicated ports can't carry the default gateway.
  • Unused ports: leave them disabled, and never configured on an active subnet.
  • Global settings: hostname, DNS suffix, nameservers, hosts table; TCP keep-alive time/probes/interval (how long half-dead sockets linger); HTTP→HTTPS redirect (off by default — browse to https:// explicitly); URL whitelist for anything the web UI is allowed to reach out to (R143+).
  • IPv6 exists (disabled by default): web/database access supported, project download works, but live data in ACSELERATOR over IPv6 is not. Address goes in brackets: https://[fdd2::1].

4Troubleshooting & fine print

  • Works locally, dies remotely → missing or wrong default gateway on the device (§1's animation). One-way traffic → same, or a wrong mask putting the peer "on-subnet" when it isn't.
  • Intermittent losses on a multi-NIC RTAC → check for two interfaces sharing a subnet, one of them unplugged or on the wrong switch. The manual's own worked failure.
  • Ping fails but comms work (or vice versa) → per-NIC Enable PING setting; and remember ICMP proves reachability, not that DNP's TCP port is open.
  • Time-outs only on idle connections → TCP keep-alive settings on the RTAC vs. firewall idle timers between it and the master.
  • Duplicate IP → intermittent, ARP-dependent chaos; the RTAC's ARP table (PRP diagnostics page shows one) and switch MAC tables are the fastest way to find the second claimant.
